# CM5 AI Service Plan — adversarial audit record (2026-08-07)

Four skeptics attacked CM5_AI_SERVICE_PLAN.md before it hardened, each
instructed to REFUTE claims in one dimension (firmware feasibility /
protocol arithmetic / host-side stack / security + conventions). Zero
claims were refuted outright; the 14 WEAKENED findings below were folded
into the plan in place (see the plan's §10 for the summary). This file is
the full verdict-by-verdict record. The raw investigation that produced
the plan is in investigation/ (six structured findings files).

Severity/verdict counts: firmware 13 (5 HIGH-SURVIVES, 4 WEAKENED);
math-protocol 11 (1 HIGH-WEAKENED); host-stack 11 (1 HIGH-WEAKENED);
security-conventions 8 (1 MEDIUM-WEAKENED). No CRITICAL, no REFUTED.

# CRITIC: firmware

OVERALL: The plan survives the firmware-feasibility attack unusually well: every file:line citation I checked resolved to exactly the claimed code in the working tree (HAL_Audio lease at :184, snip fork at ESPSR:2133/2183, espnowmessages at :16821, oledtext/g2notify at :6589/:17939, fileread admin at :1277, per-call HAL UART mutex at :1229-1237, SOURCE_UART power-save exclusion, and the ~1.3MB headroom which computes to 1.30MB against the actual XIAO binary). The two substantive weaknesses are both in Gap C1/P3 scoping and the P0 bench logic: the "9-function seam" understates the real remote-backend surface (llmFramePrompt is hardwired into chatBeginTurn/chatRetryLast so remote prompts get Q:/A: framing without chat-layer edits; the result globals are file-static so llmpush and dispatch must live in System_LLM.cpp; D5(b) implicates a much larger symbol set), and P0's WER data comes from firmware-processed micrecord audio while A1/A2 ship raw pre-gain snips, so the ship-RAW decision cannot be validated by the P0 bench as written. Neither breaks the architecture — they re-scope P3's file plan and P0's evidentiary value.

## [HIGH] SURVIVES: §3 TX ownership: HAL mutex is per-call only (esp32-hal-uart.c:1229-1237), any second writer can split a reply, ≤1KB frames bound the stall to ~11ms, and uartLinkStop-takes-the-mutex fixes the lifecycle race sPending no longer covers

Math: 1024B×10 bits @921600 = 11.1ms. TX ring 4096 with no flow control always drains (System_UartLink.cpp:103-109). B2's same-task interleave-safety claim also verified (replies and any tick-drained push queue share the loop task).

# CRITIC: math-protocol

OVERALL: The plan's protocol and arithmetic layer largely survives a hostile recompute: every throughput, transfer-time, chunk-count, and baud-divider number checks out against the working tree (fileread's actual rawCap formula yields 2,904 B/reply vs the claimed ~2,880; 2M is genuinely divider-exact on both the S3 XTAL-40MHz path and the RP1 PL011 at 48MHz/16; the 0x00-free text channel is structurally guaranteed by the C-string reply pipeline). Two claims weakened: the "~11ms" TX-stall bound only covers ≤1KB frame writers while the plan simultaneously keeps unframed 4095B single-write replies whose worst-case mutex hold is ~44ms (matters for A2 staging-ring sizing), and the poll/push discovery-latency figures are mean-only, hiding a tail of one full poll interval plus up-to-60s cmd_exec occupancy and documented 200ms+ loop stalls. Neither weakness invalidates the phasing; both need one-line corrections so P2/P4 sizing is done against worst case, not the mean. Sources consulted for the RP1 PL011 clock: https://forums.raspberrypi.com/viewtopic.php?t=361321 and https://forums.raspberrypi.com/viewtopic.php?t=368930.

## [HIGH] WEAKENED: §3 TX ownership: "Frames stay ≤1KB so a full TX ring can't stall a writer holding the HAL mutex for more than ~11ms of wire time"
EVIDENCE: 1KB frame into a full 4096B TX ring blocks until 1024B drain = 1024*10/921600 = 11.1ms — that arithmetic is right, but it bounds only ≤1KB FRAME writers. The same plan keeps replies unframed through A0/A1 ("Replies keep their current shape", §3) and converts the reply site to SINGLE-write output: a max reply is 4095B+\n = 4096B (CMD_RESULT_MAX=4096, System_CommandTypes.h:120; write at System_UartLink.cpp:290-291) — one write() into a congested ring holds the new link TX mutex for up to 4096*10/921600 = 44.4ms, 4x the stated bound. During A2 streaming (32 frames/s = one frame every 31.25ms) an audio producer blocked 44ms behind a reply needs ≥2 frames of staging headroom.
CORRECTION: State the real worst-case TX-mutex hold as ~44ms (unframed 4095B reply) until replies are framed too; size the A2 PSRAM staging ring for ≥2-3 frame periods of writer stall, or split reply writes into ≤1KB mutex slices when the frame writer lands.

## [HIGH] SURVIVES: §3 TX framing: 0x00 "a byte that never occurs in the text channel" — is that actually guaranteed for reply payloads today?
EVIDENCE: Attacked via every wire-writer: the only TU writing UART_LINK_PORT is System_UartLink.cpp (grep over components/hardwareone). All reply bytes transit NUL-terminated C-string chokepoints: handler → ExecReq::out (char[4096]) → `out = r->out` C-string String assignment (System_Utils.cpp:5026) → write(out.c_str(), out.length()); uartWriteLine uses strlen (System_UartLink.cpp:68-71). An embedded 0x00 is structurally truncated before reaching the wire. The one raw-binary emitter, fileread `bin`, is gated on ctx.transport==SOURCE_BLUETOOTH + established Secure Channel and falls through to b64 otherwise (System_Filesystem.cpp:950-955) — unreachable over UART. Caveat that does NOT break the claim but must be designed for: between sessions the wire DOES carry 0x00s — ROM boot bursts at 115200 read at 921600 and break conditions decode as 0x00 (CM5_CARRIER_DESIGN_BRIEF.md:202 documents the boot spew) — so demux resync must rely on CRC-rejecting garbage frames, not on 0x00 scarcity alone.

## [HIGH] SURVIVES: §1.1/§6 D3: "2,000,000 baud (divider-exact both ends, PL011 caps at 3M)"
EVIDENCE: S3 end verified from HAL source: on S3 the Arduino HAL pins the UART source to XTAL (UART_SCLK_XTAL, esp32-hal-uart.c:914-915), 40MHz. 40e6/2e6 = 20 — integer-exact, immune to CPU scaling. Cross-checks: 921600 → best divisor 43+6/16=43.375 → +0.064% (matches link-plan's "~0.06%", UART_HOST_LINK_PLAN.md:255); 3M → 13+5/16 → +0.157% (matches "0.16%"). Pi end: RP1 PL011 clk_uart ≈ 48MHz, cap = 48e6/16 = 3.0M — matches the plan's "PL011 caps at 3M" and is corroborated by RPi forum/RP1 discussion (https://forums.raspberrypi.com/viewtopic.php?t=361321, https://forums.raspberrypi.com/viewtopic.php?t=368930) AND by the bench link already running 921600 on ttyAMA2 (impossible under the 9.216MHz debug-uart clock, which caps at 576k). 2M divisor = 48e6/(16×2e6) = 1.5 = IBRD 1 + FBRD 32/64 — exactly representable, zero average-frequency error (fractional-divider sample jitter ~1/24 bit, well inside 8N1 tolerance). 33Ω series into ~10-20pF pad = sub-ns RC vs 500ns bits — no SI issue. Residual: RP1 clk_uart is asserted from secondary sources, not an in-repo doc — D3's planned loopback soak at 2M is the right closing test.

## [MEDIUM] WEAKENED: §Gap B1: "Latency cost of polling: half the poll interval, ~100-250ms" and B2: "Cuts job-discovery latency to one loop lap (~2-16ms)"
EVIDENCE: T/2 arithmetic is correct for 2-5Hz (T=200-500ms → mean 100-250ms), but it is the MEAN only. Worst case = full interval (500ms at 2Hz) + drain serialization: the poll reply requires submitAndExecuteSync, which blocks the loop task on cmd_exec_task for up to 2s queue + 60s semaphore (System_Utils.cpp:4975, 5005) behind any long-running command, and UART_HOST_LINK_PLAN.md:220-221 documents 200ms+ loop stalls under load — the same tail breaks B2's "~2-16ms" (loop floor is delay(2), HardwareOne.cpp:2792, but the stall tail is 100x that). The 2-5Hz SAFETY half of the claim survives: SOURCE_UART is excluded from powerSaveNoteActivity exactly as cited (System_Utils.cpp:4587-4589) and 5 polls/s against ~60-500 laps/s is negligible.
CORRECTION: Quote discovery latency as "mean T/2 (~100-250ms), tail = one poll interval + cmd_exec occupancy (unbounded behind a long command; documented 200ms+ loop stalls)"; note the voice-job FSM should not sit behind a 2Hz poll while cmd_exec is occupied if snappiness matters.

EVIDENCE: fileread caps the raw read so the b64 reply fits ExecReq::out: rawCap = ((4096 − 192 − pathLen)/4)×3 (System_Filesystem.cpp:887-925, OUT_CAP=4096=CMD_RESULT_MAX). Actual micrecord path "%s/rec_%lu.wav" ≤30 chars (System_Microphone.cpp:376-377) → rawCap=2904; plan's 2,880 corresponds to a 64-char path — conservative by <1%. ## [MEDIUM] SURVIVES: §1.1/§9: "Classic-ESP32 boards cap at 230,400 = 23,040 B/s < 32,000: live PCM is structurally S3-only"
EVIDENCE: UART_LINK_BAUD_MAX = 230400 on every classic board block (System_BuildConfig.h:803-804, 833-834, 1050-1051) and the clamp is enforced at System_UartLink.cpp:88-90. The cap is firmware policy but physically grounded: HAL selects REF_TICK (max 250kbps per esp32-hal-uart.c:919 comment) for ≤250k on classic; above that it clocks off APB, which drifts under the power-save CPU scaling this firmware uses (System_BuildConfig.h:796-798 rationale). 230400/10 = 23,040 B/s < 32,000 B/s PCM ✓ — and even 250k (25,000 B/s) wouldn't clear it, so "structurally S3-only" holds for raw PCM.

## [MEDIUM] SURVIVES: §9: "CM5→XIAO audio streaming — RX ring is 4096B (=128ms) against documented 200ms+ loop stalls; silent overflow guaranteed"
EVIDENCE: setRxBufferSize(4096) confirmed (System_UartLink.cpp:108); 4096 B / 32,000 B/s = 0.128s ✓; the 200ms+ loop-stall figure is documented at UART_HOST_LINK_PLAN.md:220-221 ("no realistic buffer survives a documented 200ms+ loop stall under streaming"). A 200ms stall at 32,000 B/s inbound = 6,400 B > 4,096 B ring → overflow, and the UART driver drops silently (no flow control: SERIAL_8N1, no CTS/RTS pins configured; carrier reserves GPIO6/7 for a future rev, CM5_CARRIER_DESIGN_BRIEF.md:136). Rejection is sound.

## [MEDIUM] SURVIVES: §3 TX-mux premise: "today every TX sequence is two write() calls from the loop task; the HAL mutex is per-call only (esp32-hal-uart.c:1229-1237)"
EVIDENCE: uartWriteBuf at esp32-hal-uart.c:1229-1237 takes UART_MUTEX_LOCK/UNLOCK around a single uart_write_bytes — per-call scope confirmed. The reply is exactly two write() calls (payload then '\n', System_UartLink.cpp:290-291), as is uartWriteLine (:68-71) — a second writer can interleave between them, so the uartLinkWriteFrame mutex is genuinely needed for A1/A2, not defensive fiction.

## [LOW] SURVIVES: §3 A1 framing: CRC16 per ≤1KB chunk is sufficient integrity for the audio path
EVIDENCE: Plan states no explicit BER, so tested at a pessimistic 1e-8 for a point-to-point 3.3V on-carrier trace: 1KB frame ≈ 8,272 wire bits → P(corrupt frame) ≈ 8.3e-5; CRC16 undetected fraction ≤ 2^-16 = 1.53e-5 → ≤1.3e-9 undetected/frame; at 32 frames/s that is one undetected error per ~8,900 days, and the payload is PCM where a slipped bit is one click. ## [HIGH] WEAKENED: §2/§4.1: 'Language: Python first... the link client is pyserial + asyncio; Nothing in the hot path needs C++' — implicitly asserting Python asyncio + pyserial sustains 92KB/s inbound A1/A2 bursts without loss (CM5_AI_SERVICE_PLAN.md:128-131, 252-259, 267-273)
