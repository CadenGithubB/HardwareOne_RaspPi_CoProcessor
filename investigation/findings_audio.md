# audio

## Summary
Audio capture on the XIAO S3 Sense is already unified behind HAL_Audio (components/hardwareone/HAL_Audio.cpp) — the "unified mic source layer" from memory has been BUILT. It is a single-owner, destructive-pull stream: every source delivers canonical 16 kHz / mono / int16 PCM via audioReadPcm(); exactly one owner ("mic" sensor module or "sr" ESP-SR) may hold capture at a time, and a second audioReadPcm caller would steal samples, so any CM5 feed must be forked inside the owner's loop, not opened as a second capture. On the current xiao_s3 working tree the only source is the onboard PDM mic on I2S0 (CLK=GPIO42, DATA=GPIO41); the G2 BLE mic path compiles to stubs because boards/xiao_s3.defaults sets CONFIG_BT_ENABLED=n and System_BuildConfig.h has ENABLE_BLUETOOTH 0. Record-to-WAV exists and works on PDM today: openmic → micrecord start/stop writes 16-bit mono WAV to /sd/recordings (SD preferred) or /recordings (LittleFS), capped at 60 s, via a dedicated "mic_record" task (core 1, HIGH prio) reading 4096-byte chunks through audioReadPcm.

ESP-SR is currently compiled out (ENABLE_ESP_SR 0, System_BuildConfig.h:293) but is deliberately enableable on the 8 MB flash: partitions_sr_8mb.csv (factory 4992K + model 3008K + littlefs 128K) exists and the top-level CMakeLists auto-selects it when the flag flips; sdkconfig.defaults already carries the esp-sr model config (MODEL_IN_FLASH, WN9_HILEXIN wake word, MultiNet7-EN-quant, CN disabled) and esp-sr is a managed component. Today's XIAO binary is 4,098,352 B, leaving ~1.0 MB of the 4992K SR-layout factory partition for the esp-sr inference code — a plausible but UNVERIFIED fit, and docs/ESPSR_VOICE_TABLE_PLAN.md:70 records that SR has never been hardware-validated on the current boards. Wake-word-only operation is structurally supported: startESPSR tolerates MultiNet init failure and continues with WakeNet alone, and the model partition could shrink to ~300K (WN9 only) if the CSV is edited, reclaiming ~2.7 MB for LittleFS.

The tap point for forking utterance PCM to a CM5 streamer already has a proven precedent: the srTask loop pushes every raw post-read chunk into the "snip" subsystem (System_ESPSR.cpp:2133-2138) — an 800 ms PSRAM pre-roll ring plus a up-to-6 s PSRAM session buffer that is queued to a writer task on wake detection. A UART streamer is a third consumer at exactly that line (or a HAL_Audio fan-out). Critical detail: that tap carries RAW pre-gain PCM — applyMicAudioProcessing (DC removal, HPF, pre-emphasis, ~24x software gain) is applied only to the AFE feed copy at System_ESPSR.cpp:2183 — so the CM5 STT either takes quiet raw PDM audio or the fork point must run the processing chain itself.

Shipping the utterance: the UART link is a newline-framed TEXT channel (2047 B line cap in, CMD_RESULT_MAX=4096 reply cap out, one command per loop lap, no flow control, TX always drains at wire rate). 5 s @16 kHz/16-bit = 160,000 B. Raw wire-time floor: 1.74 s @921600 (92,160 B/s), 0.80 s @2M (both baud rates are divider-exact; UART_LINK_BAUD_MAX=3,000,000 matches the Pi PL011 cap). Base64 adds 4:3 → 2.31 s / 1.07 s. Live streaming (32,000 B/s) uses only 35% of 921600 capacity so it keeps up in real time — but every non-CLI option requires new framing, which docs/UART_HOST_LINK_PLAN.md:330-331 explicitly deferred ("bulk/file transfer framing … separate design"). The only zero-firmware-change path today is micrecord + admin-gated fileread b64 chunks (~2,880 raw B per 4 KB reply → ~56 round trips → ~2.5 s wire minimum, realistically 4-8 s), and on the SR partition layout LittleFS shrinks to 128K so recordings must target SD.

## Constraints
- HAL_Audio capture is EXCLUSIVE single-owner with destructive pull: a CM5 streamer must be fed from the current owner's read loop (srTask tap at System_ESPSR.cpp:2133 or recordingTask) or via a new fan-out inside HAL_Audio — it can never call audioReadPcm as a second consumer (HAL_Audio.h:8-26, HAL_Audio.cpp:184-193)
- SR and mic-sensor recording are mutually exclusive today: startESPSR force-stops the mic module and takes the 'sr' lease (System_ESPSR.cpp:2598-2617)
- ESP-SR input rate is fixed 16 kHz mono int16 (I2S_SR_SAMPLE_RATE, System_ESPSR.cpp:58); any concurrent CM5 STT feed inherits that format from the shared stream
- On xiao_s3 the ONLY mic source is the onboard PDM (BT off in boards/xiao_s3.defaults → G2 mic stubs); plans must not assume the G2 mic on this board
- UART link reply envelope is hard-capped at 4095 B + NUL (CMD_RESULT_MAX, System_CommandTypes.h:120) and inbound lines at 2047 B; one command per loop() lap; no flow control; text/newline framing — any raw-binary or streaming transport is NEW protocol work explicitly deferred by docs/UART_HOST_LINK_PLAN.md:329-331
- Enabling ENABLE_ESP_SR on the 8 MB XIAO swaps to partitions_sr_8mb.csv: LittleFS collapses to 128K (recordings/models must live on SD) and every flash reflash across layouts erases on-device files; binary fit in the 4992K factory partition is unverified (current bin 4,098,352 B + esp-sr code)
- SR on current boards has never been hardware-validated (docs/ESPSR_VOICE_TABLE_PLAN.md:70) and the pre-1.0 convention is bench HW test before commit
- fileread (the only existing pull-a-file path) is admin-gated and base64-only over UART ('bin' raw mode is BLE-only) — CM5 file pulls need an admin session or a new scoped capability (System_Filesystem.cpp:880-885,1277)
- The srTask tap carries RAW pre-gain PCM (processing applied only to the AFE copy at System_ESPSR.cpp:2183); DSP chain state is shared mic/SR global state — forking processed audio requires care not to double-run the stateful filters
- Task-stack macros are BYTES not words (MIC_RECORD_STACK_WORDS=4096 B, SR_STACK_WORDS=8192 B, System_TaskUtils.h:111-113); task policy pins compute to core 1; avoid per-action task spawning (standing feedback)
- Serial0/UART0 has exactly one writer discipline today (loop-task drain); a streamer task writing the same port must not interleave bytes inside a command reply — needs a TX mux/framing rule
- MAX_RECORDING_SEC=60 caps micrecord; snip session caps at gSrSnipMaxMs=6000 ms pre-tuning — utterance windows longer than 6 s need the cap raised (both are trivial constants)
- No secrets in PSRAM is a standing rule, but audio PCM in PSRAM is established practice (all mic/SR buffers already prefer PSRAM)

## Options
### (a) Live-stream frames over UART during capture
Fork each ~32-128 ms raw chunk at the srTask tap (System_ESPSR.cpp:2133) or from a mic-module consumer into a paced writer that frames PCM onto Serial0 (length-prefixed binary frames or base64 lines interleaved with the command channel). 32,000 B/s stream = 35% of 921600 baud capacity (16% at 2M), so it runs in real time; the CM5 has the full utterance <~0.2 s after speech ends — the only option that supports streaming STT/endpointing on the CM5.
Pros: Lowest end-to-end latency by far (CM5 can start decoding while the user is still speaking); Bandwidth verified feasible at the default 921600 baud with headroom for interleaved command traffic; Wake-word-only SR on-device + STT on CM5 is the natural split: WakeNet gates the stream, MultiNet (2.6 MB flash + PSRAM) can be dropped; Snip machinery already demonstrates per-chunk forking without disturbing the AFE feed
Cons: Requires the deferred new framing/mux protocol on a channel designed request/response (docs/UART_HOST_LINK_PLAN.md:102-107,329) — stream frames and 4 KB command replies must not interleave mid-message; Needs a TX ownership rule (single-writer discipline) plus backpressure policy for the no-flow-control wire; Raw pre-gain PCM at the tap: decide raw-vs-processed and where gain runs; New firmware surface: start/stop stream command, framing, session auth binding
### (c) Record to PSRAM ring, then burst-transfer
Reuse/extend the snip pattern (800 ms pre-roll ring + PSRAM session buffer, System_ESPSR.cpp:1213-1344): capture the utterance into PSRAM (160 KB for 5 s; 8 MB octal PSRAM makes even 60 s = 1.9 MB trivial), then ship it with ONE new bulk command using length-prefixed raw binary (or b64) frames. Post-utterance transfer: 1.74 s raw @921600, 0.80 s @2M (2.31/1.07 s if base64).
Pros: No filesystem in the loop — no FsLock contention, no LittleFS 128K problem on the SR layout, no SD wear; Snip subsystem already implements ring + session + async hand-off; the 'writer' just becomes a UART sender instead of a WAV file; Simpler framing than (a): one bounded burst per utterance, natural place for a checksum; Works identically whether SR (wake-triggered) or an explicit CM5 'record now' command starts the session
Cons: Adds 0.8-2.3 s of post-utterance latency before the CM5 even starts STT — worst interactive feel except (b); Still requires the deferred bulk-framing protocol (same TX-mux problem as (a), just burst-shaped); Utterance length capped by buffer sizing decisions (snip default 6 s)
### (b) Record to file (micrecord), transfer via existing CLI (fileread)
Works today with ZERO firmware changes: CM5 sends openmic, micrecord start, micrecord stop (reply contains the WAV path), then loops admin-gated fileread "<path>" <off> <len> b64 (~2,880 raw B per 4 KB reply, ~56 round trips for 160 KB → ≥2.5 s wire minimum at 921600, realistically 4-8 s with per-call exec + turnaround), then micdelete. WAV format is self-describing (sample rate in header).
Pros: Zero firmware changes — could be prototyped on the bench today over the verified link; WAV file doubles as an on-device artifact (debugging, replay, training data); Round-trip-per-chunk structure is naturally flow-controlled and restartable
Cons: Slowest: multi-second post-utterance transfer plus VAD/endpointing must be done by CM5-issued stop commands (no auto-endpoint); fileread is admin-gated — CM5 session needs admin, weakening the isolation story flagged in the plan doc (D3); On the SR partition layout LittleFS is 128K → requires SD card mounted/writable; FS writes take FsLockGuard and contend with other FS users; micrecord can't run while SR runs (exclusive owner) — no wake-word-triggered capture without new glue; file reopened/seeked every chunk adds per-call cost

## Open questions
- Does the xiao_s3 binary + esp-sr inference libs (WakeNet9 + optional MN7 + esp-dsp/esp-nn) actually link under the 4992K SR-layout factory partition? Current bin is 4,098,352 B; needs a real ENABLE_ESP_SR=1 build to answer (also whether IRAM/DRAM survive)
- Runtime PSRAM and core-1 CPU cost of AFE(SE+VAD)+WakeNet on this board, and whether it coexists with concurrent camera streaming (PSRAM bus contention on octal) — nothing measured in-repo; srTask and camera work are both core-1 compute
- Wake-word-only build shape: keep the 3008K model partition (littlefs 128K) or cut a new partitions CSV with a ~320K WN-only model partition reclaiming ~2.7 MB for LittleFS? (CMake picks by SR flag + flash size only; a third axis would be new logic.) Alternative: srModelSource=1 loads models from SD, avoiding the model partition entirely — but does esp_srmodel_init from SD keep model data in PSRAM, and is boot-order SD-mount guaranteed?
- Framing/mux design for options (a)/(c): reuse the deferred MSG_ROUTE_UART sink bit (255 B clamp makes it wrong for PCM) vs a new binary length-prefixed frame type on the same wire vs a second UART; and who owns Serial0 TX when a stream and a command reply collide
- Should CM5-bound audio be raw pre-gain PCM (tap default) or run through applyMicAudioProcessing (24x gain, HPF, pre-emphasis tuned for WakeNet)? CM5-side STT (e.g. Whisper) may prefer raw + its own AGC; firmware-side processing double-drives shared filter state if both consumers run it
- Is 2M (or 3M) baud stable on the physical 3-wire XIAO↔Pi5 ttyAMA2 link? Both ends are divider-exact/within spec per the plan doc, but no hardware test at >921600 is recorded
- Endpointing ownership for the record-then-send options: AFE VAD state is available in srTask (fetchResult->vad_state, System_ESPSR.cpp:2234) — should firmware auto-end the utterance on VAD silence (snip-style deadline) or should the CM5 command the stop?
- Auth/authz model for the audio surface: new stream/burst commands should presumably be requiresAdmin=false but bound to the UART session user; does utterance audio count as sensitive enough to gate behind a per-user permission (cf. guest role audit)?
- If the mic sensor module (not SR) is the capture owner (no wake word, CM5-triggered capture), does the CM5 want the existing 'mic' owner path extended with the same tap, so streaming works in both ownership modes?
