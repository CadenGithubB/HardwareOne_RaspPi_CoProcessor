# initiative

## Summary
The link as implemented (System_UartLink.cpp, verified in the working tree) is strictly half-duplex request/response: uartLinkTick() runs once per loop lap (HardwareOne.cpp:2784), drains at most one line, executes it SYNCHRONOUSLY via submitAndExecuteSync on the loop task (blocking the whole UI/sensor loop up to 60s worst-case), and writes the one reply itself (blob + newline, two port writes). outputMask=MSG_ROUTE_FILE with captureOutput=false means no broadcast/debug line can ever reach the wire — which simultaneously guarantees channel cleanliness and means broadcast-style commands (including cmd_events, System_Events.cpp:402-431) return only "OK" to the CM5; any poll command for this channel must return a JSON document in the command return value. There is no pending-queue "hostjobs" concept anywhere; the confirm machinery (System_CLIConfirm.h) is a single-slot CLIMode, not a queue. The two real in-repo precedents for initiative reversal are (1) espnowmessages — cursor-paged JSON polling of asynchronously-arriving results (sinceSeq merge, System_ESPNow.cpp:16821, 17428-17496), and (2) the typed event ring's independent-cursor consumer API (systemEventFetchSince, System_Events.cpp:278-310) with three live consumers; both clone cleanly into a CM5 poll command. The pushier alternatives verify as costly: the MSG_ROUTE_UART sink would burn the last routing bit 0x80 (System_Debug.h:25-32,211 — confirmed) with a 255B [CUT] clamp (System_Debug.h:199, System_Debug.cpp:974-978) and a cross-task writer hazard (sink writes come from debug_out, System_Debug.cpp:209, while replies are two HAL-lock-per-call writes from the loop task); a hardware doorbell is impossible on the current carrier (only TX/RX/power are routed; CM5 GPIO6/7 reserved unconnected — CM5_CARRIER_DESIGN_BRIEF.md:133-136). The cheapest genuinely-push option is a loop-task-owned push queue drained inside uartLinkTick with a reserved line prefix — structurally interleave-safe because the same task writes replies, at the cost of client-parser discipline (json-form single-line replies).

For the voice flow, the driver should be a loop-tick FSM plus flag/queue handoffs, not a new task: the policy header (System_TaskUtils.h:148-178) and memory both forbid per-action tasks, and the codebase already demonstrates the exact shape three times — uartLinkTick's pending-flag lifecycle, the hierarchical VoiceState machine running on sr_task (System_ESPSR.cpp:220-231, core 1, 8KB), and automations submitting via the non-blocking submitCommandAsync (System_Utils.cpp:5041; System_Automation.cpp:98-116). Voice identity plumbing exists (voicearm binds a real user; matched phrases execute as that user with SOURCE_VOICE — System_ESPSR.cpp:177-211, 3874). The hard unsolved piece is moving captured audio to the CM5: HAL_Audio is an exclusive-lease capture layer (SR and recording are mutually exclusive), the link has no bulk framing (explicitly deferred), replies cap at 4095B, and the existing chunked envelope (fileread b64) is admin-gated while the CM5 daemon is planned as 'user' tier.

Results coming BACK to humans have three working paths today, all reachable by the CM5 as ordinary commands over the link: oledtext (OLED custom-text page, non-admin, OLED_Utils.cpp:6589), g2notify (transient G2 text, non-admin, G2_Glasses.cpp:17939), and the automatic fact that every command's broadcast lines are force-routed to OLED|G2 (System_Debug.cpp:967-968). The notification system can push native G2 cards but only for typed SYSEVT kinds and no command posts arbitrary events — a SYSEVT_HOST_* kind would be the idiomatic extension. TTS does not exist and cannot: HAL_Audio is capture-only; the XIAO has no audio output path at all. On cadence: lap floor is delay(2), normal laps are expected <16ms, the stall threshold is 200ms (HardwareOne.cpp:999), and the SOURCE_UART power-save exclusion shipped exactly as planned (System_Utils.cpp:4585-4590), so a polling CM5 neither holds the device awake nor trips LOOPHEALTH as long as each poll command is fast — but every poll does freeze the loop for its exec round trip, and PBKDF2 login (~12s) plus OTA-probation heartbeat gaps remain the documented pathological cases. Auth fit: pattern A runs entirely at 'user' tier today (events/espnowmessages/oledtext/g2notify are all non-admin); pattern B needs a new opt-in setting plus a decision on gUartAuthed gating and per-kind visibility (the notification device-policy layer is a reusable model); patterns needing file pulls need admin or a new scoped capability; and the event ring must be redacted for a machine feed because SYSEVT_REMOTE_CMD_RX detail can carry plaintext credentials (System_Automation.cpp:3784-3791).

## Constraints
- Link framing today: request/response only; reply is ONE blob (<=4095B, CMD_RESULT_MAX 4096, System_CommandTypes.h:120) + '\n', written as TWO port writes (System_UartLink.cpp:290-291); inbound line cap 2047B (System_UartLink.cpp:61); one command per loop lap (System_UartLink.cpp:337)
- The UART drain runs the command SYNCHRONOUSLY on the loop task: submitAndExecuteSync blocks up to 60s (abandon path HardwareOne.cpp:790-804), freezing display/G2/sensor ticks for the duration — true long-polling is architecturally impossible; every CM5 poll must be a fast command
- Only ONE routing bit remains: routing is uint8_t (System_Debug.h:211), bits 0x01-0x40 assigned (System_Debug.h:25-32), so MSG_ROUTE_UART would burn 0x80 forever; any sink line is clamped to 255B with [CUT] (DEBUG_MSG_SIZE 256, System_Debug.h:199; clamp System_Debug.cpp:974-978)
- Sink consumption happens on the debug_out task (debugOutputTask, System_Debug.cpp:209) — a MSG_ROUTE_UART sink adds a second task writing UART_LINK_PORT; the HAL mutex is per-write-call only (uartWriteBuf, components/arduino/cores/esp32/esp32-hal-uart.c:1229-1237), so a sink line can land between the reply blob and its newline unless the reply becomes a single write or all pushes go through the loop task
- Carrier hardware: ONLY UART TX/RX + switched 5V/GND reach the XIAO socket; CM5 GPIO6/7 are reserved-but-UNCONNECTED (future CTS/RTS, docs/CM5_CARRIER_DESIGN_BRIEF.md:133-136); no I2C/SPI by explicit design (:157-159); no reset line (:155) — any GPIO doorbell or second UART needs a carrier revision
- TTS / audio playback does not exist anywhere: HAL_Audio is capture-only (single-drainer 16kHz/mono/int16 lease model, HAL_Audio.h:1-27); grep for tts/speak/play paths is negative — CM5 answers can only be displayed (OLED/G2/web), not spoken by the XIAO
- Audio capture is an exclusive lease: ESP-SR holds it via audioCaptureStart("sr") (System_ESPSR.cpp:1650-1658); recording and SR are mutually exclusive (HAL_Audio.h concurrency model A) — a capture-for-CM5-STT flow must take or borrow the lease
- No bulk-transfer framing exists on the link (explicitly deferred, docs/UART_HOST_LINK_PLAN.md:330-331); fileread's chunked b64 envelope exists but files/fileread/filewrite are ALL admin-gated (requiresAdmin=true, System_Filesystem.cpp:1268-1285) while the CM5 daemon is planned as 'user' tier (plan D2/D3)
- No-per-action-tasks policy: prefer loop-tick modules over xTaskCreate (memory + System_TaskUtils.h:148-178); compute pins to core 1, radio/IO and the main loop live on core 0 — 'the loop is on the other core' is never a race argument (System_TaskUtils.h:157-159)
- cmd_events is invisible over the UART link: it emits via BROADCAST_PRINTF and returns "OK" (System_Events.cpp:402-431); with outputMask=MSG_ROUTE_FILE + captureOutput=false (System_UartLink.cpp:281-283) the CM5 receives only "OK" — any poll command for this channel MUST return its document in the return value (only 'events kinds json' does today, System_Events.cpp:335-372)
- Event-ring content is sensitive: SYSEVT_REMOTE_CMD_RX detail[] carries raw remote command text including possible 'login <user> <pass>' (documented System_Automation.cpp:3784-3791) and 'events' is requiresAdmin=false (System_Utils.cpp:2696) — a CM5-facing event feed needs redaction or per-kind gating
- ORIGIN_UART is structurally excluded from physical-presence commands (cmdOtaPin etc. key on ORIGIN_SERIAL exactly, System_CommandTypes.h:50-54); SOURCE_UART is excluded from powerSaveNoteActivity alongside SOURCE_INTERNAL (System_Utils.cpp:4585-4590) — SHIPPED, so a polling CM5 cannot hold the device out of power-save
- OTA probation: loop heartbeat gates image validation (HardwareOne.cpp:2794-2801); long UART-triggered stalls (>5s) postpone validation — CM5 daemon must idle during probation (client-side rule)
- No backwards-compat obligations: pre-1.0, user erase-flashes all devices (standing convention); wire-protocol changes to the link are free until 1.0

## Options
### A. Cursor-paged poll command (clone espnowmessages)
Add a 'hostjobs'/'hostevents json [sinceSeq]' command returning a JSON document in the return value (espnowmessages pattern, System_ESPNow.cpp:16821/17428-17496), backed by either a new host-job registry or a dedicated systemEventFetchSince cursor (System_Events.cpp:278). Voice/button triggers post a job; the CM5 discovers it on its next poll, does STT/LLM, and delivers the answer by running display commands (oledtext/g2notify) back over the link.
Pros: Zero changes to link framing or routing system — pure command addition, the pattern is proven twice in-repo (espnowmessages, event-ring consumers); Auth comes free: runs under the existing UART session, 'user' tier suffices, auditable like any command; CM5 remains the only initiator — no client parser changes beyond a new command; Cursor+seq gives loss accounting for free (ring-skip counters already exist)
Cons: Latency = poll interval; every poll synchronously blocks the loop task for the exec round trip, so aggressive polling (>~5-10Hz) inflates lap times and wastes cmd_exec cycles; True long-poll impossible (blocking drain) — it is pure interval polling; Ring/event exposure needs redaction for credential-bearing kinds if built on the event ring; 48-slot ring bounds how slowly the CM5 may poll before silent loss (if event-ring-backed; a dedicated job registry avoids this)
### B. Unsolicited push lines from uartLinkTick (loop-task-owned)
A small push queue (bounded, heap or static) that uartLinkTick drains after the command drain, writing prefix-disciplined lines (e.g. 'EVT: {...}') directly to UART_LINK_PORT. Producers (voice FSM, event consumers, notification hook) enqueue from any task; only the loop task ever writes the port, so pushes can never split a reply (both happen sequentially in the tick).
Pros: Lowest latency: event → next lap → wire (~2-16ms typical); No routing bit spent, no 255B sink clamp — push payload format is free (can carry JSON); Structurally interleave-safe if the loop task stays the only writer (reply is written inside uartProcessLine on the same task); Doorbell effect: CM5 can sleep on read() instead of polling — best power/CPU profile on both sides
Cons: Breaks the strict request/response contract — the CM5 client parser must separate push lines from multi-line replies; only fully clean if the CM5 sticks to json-form commands (single-line replies) per plan Phase 6; New policy surface: what may be pushed to a 'user'-tier (or AuthBypass) session, gating on gUartAuthed, opt-in setting — none exists today; Push while the host is mid-reboot/absent spews into the void (harmless but needs bounded-queue drop accounting); Firmware-side new code (queue, prefix discipline, drop policy) — small but real
### C. MSG_ROUTE_UART sink bit (plan D4's Option B)
Give the link a real routing sink: commands/subsystems address it via outputMask and debug_out writes matching lines to the port.
Pros: Reuses the entire existing routing/gating machinery (gOutputFlags lane gates, per-command masks); Live debug/event streaming to the CM5 with no new queue code
Cons: Burns the LAST free routing bit 0x80 forever (System_Debug.h:25-32, :211 — verified); Inherits the 255B [CUT] clamp (System_Debug.h:199, System_Debug.cpp:974-978) — hostile to structured payloads; Writer lives on debug_out task (System_Debug.cpp:209): cross-task interleave with the drain's two-call reply write (System_UartLink.cpp:290-291) unless the reply becomes a single write; HAL lock is per-call only (esp32-hal-uart.c:1229-1237); No session/identity filtering — raw routed output ignores who is logged in on the link; defeats the channel's no-leak design (MSG_ROUTE_FILE-only was the point); Explicitly deferred by the adversarially-verified plan (UART_HOST_LINK_PLAN.md:328-329) — 'only on demonstrated need'; a structured host-ask protocol is not that need
### D. Hardware side-channel (GPIO doorbell / second UART)
A dedicated 'attention' line the XIAO raises so the CM5 polls immediately, or a second UART for the async plane.
Pros: Cleanest separation of planes: command channel stays pure request/response; Interrupt-driven on the CM5 (GPIO edge) — zero polling
Cons: The carrier routes NOTHING but UART TX/RX + power to the XIAO socket; CM5 GPIO6/7 are reserved-unconnected for future CTS/RTS (CM5_CARRIER_DESIGN_BRIEF.md:133-136); no I2C/SPI/reset by design — requires a board revision (or a bench-only jumper on the Pi 5 stand-in); No firmware GPIO-doorbell module exists — new code plus per-board pin parameterization for six boards; Second UART costs another ~9-10KB DRAM of driver buffers and more pins that don't exist on the carrier
### E. MQTT loopback (broker on the CM5, XIAO over WiFi)
CM5 hosts mosquitto; the XIAO's existing MQTT client pushes (periodic sensor publishes, command bridge responses) and the CM5 subscribes — push exists today with zero firmware changes.
Pros: Works TODAY: mqttTick periodic publishes (System_MQTT.cpp:1257-1268) + response topic; SYSEVT_REMOTE_CMD_RX event posted per bridge command; Full pub/sub semantics, no framing invention
Cons: Requires WiFi up + reachable broker — defeats the UART-only carrier isolation model and the offline story; Bridge auth is per-message plaintext user/pass JSON (System_MQTT.cpp:421-478) with ~12s PBKDF2 per command — bad fit for a chatty daemon; MQTT result buffer truncates at 2047B silently (System_Events.cpp:343-346 note); Two transports to keep coherent (session state, audit) — the plan's whole point was one clean machine channel
### F. (Voice-flow driver) Loop-tick host-job FSM + submitCommandAsync
For 'capture + ask CM5': a small state machine ticked from loop() (like uartLinkTick), states ARMED→CAPTURING→PENDING_HOST→ANSWERED; triggers set flags from sr_task (voice target) or the input path (button); capture via the HAL_Audio lease; anything needing command execution goes through submitCommandAsync (System_Utils.cpp:5041) so the loop never blocks; CM5 learns of the job via pattern A or B above.
Pros: Respects the no-per-action-tasks policy and core-placement rules (System_TaskUtils.h:148-178) — no new task at all; Mirrors three proven shapes: uartLinkTick lifecycle flags, the sr_task VoiceState FSM (System_ESPSR.cpp:220-231), and automations' async submits (System_Automation.cpp:98-116); Voice identity model already exists: voicearm binds a real user (System_ESPSR.cpp:3874,:177-211) — the host job inherits an owner for auditing and result routing
Cons: Audio hand-off to the CM5 remains the unsolved half (see open questions) — the FSM is easy, the payload path is not; Capture-lease contention with ESP-SR: taking the mic for CM5 STT pauses on-device wake-word/command recognition unless the SR stream itself is teed (new HAL_Audio capability)

## Open questions
- Audio transport for CM5 STT is unsolved: 921600 baud ≈ 92KB/s wire vs 32KB/s canonical PCM (16kHz/16-bit mono) — raw throughput fits, but the link has no bulk framing (deferred, UART_HOST_LINK_PLAN.md:330), replies cap at 4095B, chunked-command pulls cost one loop-blocking cmd_exec round trip each, and fileread (the existing chunked b64 envelope) is admin-gated. Candidate shapes needing a design decision: (i) record-to-WAV + admin-scoped pull, (ii) a new streaming escape mode where the drain temporarily hands the port to a raw streamer, (iii) chunk commands at low rate. None validated.
- Actual loop lap time under this project's normal load (sensors + BLE + G2) has never been measured for this purpose — run `perftop` on hardware to size the maximum useful CM5 poll rate and the real push latency floor (static analysis only gives the delay(2) floor and the <16ms histogram expectation).
- Push-line policy: should unsolicited pushes require gUartAuthed, and which event kinds may a 'user'-tier CM5 session see? The notification device-policy layer (per-kind all/admin/off, System_Notifications.h:62-71) is a reusable gating model, but nothing applies it to a machine transport today; SYSEVT_REMOTE_CMD_RX credential leakage (System_Automation.cpp:3788-3791) forces either redaction or kind-filtering for any CM5-facing event feed.
- Protocol multiplexing for concurrent STT+LLM on the CM5: the link is strictly one-command-in-flight (drain blocks in submitAndExecuteSync), so concurrent jobs need job-ids in a hostjobs-style application protocol (submit job / poll status / fetch result), not link-level concurrency — the job-id scheme, queue depth, and result retention policy are undesigned.
- If any push writer other than the loop task is ever considered (e.g. a MSG_ROUTE_UART sink on debug_out), the two-call reply write (System_UartLink.cpp:290-291) must first become a single write call (or a small TX framing layer) — decide whether to make that refactor pre-emptively.
- Does the CM5 daemon stay 'user' tier? Voice capture pull (fileread) and any file-based result exchange need admin or a new scoped read capability (plan D3 deferred this 'by actual need' — the voice flow is the first concrete need).
- Where should the XIAO-side voice-capture FSM live: extend System_UartLink.cpp with a job registry + tick states, or a sibling System_HostLink module that owns jobs while UartLink stays pure transport? (Both satisfy the loop-tick/no-per-action-task policy; the split affects whether push lines and job state share the port-lifecycle pending-flag machinery.)
- Should `events` grow a `json since=<seq>` form (returning the document in the return value, mirroring espnowmessages) as general infrastructure, or should the CM5 feed be a dedicated hostjobs/hostevents command with its own redaction? The former benefits web/BLE too but widens the sensitive-ring exposure surface.
