# llm

## Summary
The on-device LLM is a pull-based, single-generation-at-a-time pipeline with one true demux point. Prompt flow: any surface (web POST /api/llm/generate, CLI/BLE/UART `llmgenerate json <prompt>`, OLED keyboard, G2 guided menu via `llmask`) converges on chatBeginTurn (System_LLMChat.cpp:306), which appends USER+empty ASSISTANT turns to a 16-slot PSRAM ring, frames the prompt via llmFramePrompt ("Q: …\nA:" scaffold, System_LLM.cpp:1219), and calls llmStartAsync (System_LLM.cpp:2507). llmStartAsync stages the prompt (1024B cap) + params into gLLMAsyncCtx and xTaskNotifyGive's a persistent worker task `llm_gen` (llmWorkerTask, System_LLM.cpp:197; 12KB static internal-DRAM stack, core 1, prio 2). The worker's token callback (System_LLM.cpp:208-217) is the single emit chokepoint: it appends decoded token strings into an 8KB PSRAM result buffer (gLLMResultBuf) guarded by three volatiles (gLLMResultLen/gLLMResultDone/gLLMSessionId). NOTHING pushes tokens to sinks — every surface pulls: the chat layer's drainEngineLocked (System_LLMChat.cpp:175-223) copies engine buffer → turn ring on every reader call; web polls GET /api/llm/result → chatReadStream (WebPage_LLM.cpp:361), OLED polls chatReadTurn (OLED_Mode_LLM.cpp:422), G2's lens worker polls a 180B tail every 250ms and pushes UPDATE_TEXT (G2_Glasses.cpp:21523-21659), and machine clients poll `llmresult json <offset>` which reads the engine buffer directly in 512B windows (System_LLM.cpp:2837-2878). Tokens never touch serial/broadcast/debug channels.

There is NO backend abstraction (no engine struct/vtable/fn-pointer) — llmGenerate is hard-wired in llmWorkerTask. But the seam is narrow and clean: the chat layer touches the engine through exactly ~9 free functions (llmIsReady, llmFramePrompt, llmStartAsync, llmStop, llmTokenize, llmGetSessionId, llmGetResultLen, llmGetResultChunk, llmIsGenerationDone, llmGetStatus — all call sites in System_LLMChat.cpp:180-212, 309, 335, 394, 421, 435). The narrowest remote-engine insertion is inside/beside llmStartAsync: a backend=remote branch that ships the framed (or unframed) prompt to the CM5 and has the link-RX path write returned text into gLLMResultBuf/gLLMResultLen, setting gLLMResultDone on completion with the same publish ordering (System_LLM.cpp:2532-2547). Everything downstream — drainEngineLocked, chat ring, web/OLED/G2 rendering, `llmresult` polling — works byte-identically with zero changes. Complications: llmIsReady() gates every entry (needs a REMOTE-ready state), llmFramePrompt's Q:/A: scaffold is local-model-specific (framing must move behind the backend switch), chatRetryLast's suppress-token path needs the local tokenizer (degrade to plain retry), and the guided menu (llmask) reads the local .bin's info block (hide when no menu — the llmMenuGroupCount==0 path already exists).

XIAO reality check: ENABLE_ONDEVICE_LLM is 0 in the working tree (System_BuildConfig.h:306 — "on for the FeatherS3. Set to 0 for the XIAO camera build"), and CMake literal-greps that line to exclude ALL LLM sources including System_LLMChat.cpp, WebPage_LLM.cpp, OLED_Mode_LLM.cpp (components/hardwareone/CMakeLists.txt:70-73, 441-457); G2's LLM lens is #if-gated too (G2_Glasses.cpp:21472). So today's XIAO build contains no LLM code, chat layer, or LLM UI at all. Re-enabling it on XIAO faces: 8MB flash → partitions_no_sr_8mb.csv gives LittleFS only 3180K (root CMakeLists.txt:131) so the ~6.3MB Q8 model must live on SD; PSRAM contention with the camera; and even on octal PSRAM only ~2x the FeatherS3's 1.6-1.7 tok/s with ctx auto-fit ~41 tokens (docs/LLM_FIRMWARE_ARCHITECTURE.md §2-3). CM5 offload therefore buys: arbitrarily large models, real multi-turn context (firmware sends only the current prompt — chatBeginTurn passes no history, System_LLMChat.cpp:335 — because ctx≈41 makes history pointless), 10-100x speed, ~7MB PSRAM freed, and no DRAM-pressure corruption risk. The design decision the planner must make is flag architecture: enable ENABLE_ONDEVICE_LLM wholesale on XIAO (pulls in engine + esp-dsp against ~1.3MB factory-partition headroom) vs. split a new chat/UI-only flag so System_LLMChat + surfaces compile with a remote-engine shim and no local engine.

Transport: the 4095B reply cap is NOT in the UART link — it is CMD_RESULT_MAX 4096 (System_CommandTypes.h:120) enforced at the executeCommand chokepoint (System_Utils.cpp:4852-4862, "result too large for this transport"); the link just writes the result + '\n' (System_UartLink.cpp:288-291) from a 4096B TX ring. Today's LLM polling commands already fit comfortably (llmresult ≤ ~3.2KB JSON, llmturns ≤ 4KB), so a CM5 client could drive the existing surface unchanged. The inverse direction — firmware shipping a prompt TO the CM5 — has no path today: the link is strictly Pi-as-client request/response (uartProcessLine, System_UartLink.cpp:298-349), so remote generation needs either firmware-initiated framed lines (new wire discipline) or a CM5 poll-for-pending-prompts + push-result command pair, which composes cleanly with the result-buffer seam above.

## Constraints
- One generation in flight at a time: engine gLLMResultDone flag + chat mutex serialize; chatBeginTurn returns 0 (busy) if a turn is streaming (System_LLMChat.cpp:314-319)
- Prompt path cap 1024B end-to-end: gLLMAsyncCtx.prompt[1024] (System_LLM.cpp:184) and sFramedPrompt[1024] (System_LLMChat.cpp:300); web POST body 2048B; UART inbound line 2047B
- Response caps: engine result buffer 8KB total (System_LLM.cpp:154); chat turn body 2048B (System_LLMChat.h:45); 16-turn ring; blocking CLI path ~480B (llmCmdBuf[512])
- Command reply ceiling CMD_RESULT_MAX=4096 (4095 usable) applies to every UART/BLE/web-CLI reply; enforced at executeCommand chokepoint (System_Utils.cpp:4852-4862) — streaming must stay chunked/polled, never one giant reply
- All LLM code (engine + chat layer + web/OLED/G2 surfaces) compiles only under ENABLE_ONDEVICE_LLM; the flag is 0 on today's XIAO build and CMake literal-greps the #define line (keep it a plain literal)
- UART link is strictly host(Pi)-initiated request/response with MSG_ROUTE_FILE masking — no firmware-initiated frames exist today; remote generation needs a new wire discipline or CM5 polling
- G2 UPDATE_TEXT rides a single 256B envelope → 180B visible tail cap (G2_Glasses.cpp:21507); OLED/G2 rendering assumes pull-based incremental reads, not push
- XIAO 8MB flash: LittleFS 3180K, factory headroom ~1.3MB — big local models are SD-only; PSRAM shared with camera on the XIAO Sense build
- llmIsReady()/LLMState gates every generation entry; remote mode must satisfy or bypass it without breaking llmstatus semantics
- Engine result-buffer publish ordering is mandatory (reset len → done=false → bump session → stage ctx → wake worker, System_LLM.cpp:2532-2547); a remote writer must preserve the same ordering for the drain/session-drift logic to stay correct
- Task stacks never in PSRAM; no secrets in PSRAM (project-wide rules)
- No backwards-compat needed (user erases before flashing); no autonomous commits

## Options
### A: Remote backend behind the llmStartAsync/result-buffer seam
Add a backend switch (setting, e.g. llmbackend local|remote) consulted in chatBeginTurn/llmStartAsync. Remote path: skip llmFramePrompt, hand the raw prompt to a CM5 link task; link RX writes returned text into gLLMResultBuf/gLLMResultLen with the existing publish ordering and sets gLLMResultDone at end-of-response. drainEngineLocked, the chat ring, web/OLED/G2 rendering, and `llmresult json` polling all work byte-identically.
Pros: Narrowest possible diff — the 9-function engine contract is already the de-facto interface; zero changes to any surface; Session-id/done semantics already handle late pollers, session drift, and instant completions (chatReadFinished); CLI/BLE/web command surface (llmgenerate json / llmresult / llmclear / llmretry / llmturns) works unchanged for remote; Local and remote backends can coexist (fallback to on-device model when CM5 is down)
Cons: Requires LLM code compiled in: either flip ENABLE_ONDEVICE_LLM=1 on XIAO (flash cost: engine + esp-dsp against ~1.3MB headroom) or do Option C's flag split first; llmIsReady/LLMState needs a REMOTE-ready notion; llmstatus JSON fields (config dims, tok/s, meanLogprob) need honest remote values or zeros; chatRetryLast suppress-tokens and the guided menu (llmask) are local-model-bound — degrade or hide; 8KB result buffer / 2048B turn cap bound remote answer length (fine for chat, truncates long CM5 outputs)
### B: CM5 as pure CLI client (zero firmware change)
The CM5 AI service does STT+LLM entirely host-side and uses the existing UART command channel only to act on results (execute device commands, post notifications, display text). The firmware LLM stack stays disabled on XIAO.
Pros: Zero firmware diff; works today over the validated UART link; No flash/PSRAM cost on the XIAO camera build; CM5 owns history/model/params naturally
Cons: No reuse of the chat UI: OLED/G2/web LLM pages don't exist in the build, so streamed answers have no native display surface; Every display update burns a full command round-trip and is bounded by 4095B replies and whatever display commands exist; Firmware cannot initiate (user asks a question on-device → nothing happens unless CM5 polls for it)
### C: Flag split — chat layer + surfaces without the engine, remote shim implements the engine contract
Introduce a new compile flag (e.g. ENABLE_LLM_CHAT) that builds System_LLMChat.cpp, WebPage_LLM.cpp, OLED_Mode_LLM.cpp and the G2 lens without System_LLM*.cpp; a small System_LLM_Remote.cpp implements llmIsReady/llmStartAsync/llmGetResultChunk/llmGetResultLen/llmIsGenerationDone/llmGetSessionId/llmStop (+ stub llmTokenize/llmGetStatus/llmFramePrompt/menu accessors) backed by the CM5 link.
Pros: XIAO gets the full chat UX (OLED/G2/web) with no engine or esp-dsp flash cost and no PSRAM claim; Cleanest layering — makes the implicit 9-function contract explicit and testable; FeatherS3 keeps local engine; XIAO ships remote-only; same chat layer both ways
Cons: Largest refactor: headers gate on ENABLE_ONDEVICE_LLM throughout (System_LLM.h, System_LLMChat.h, ~10 #if sites in G2_Glasses.cpp, CMake gating, settings table ownership since llmSettingEntries lives in System_LLM.cpp); Board-gated code hides compile breaks — both flag combinations must be build-verified (known project footgun); Settings/commands split is awkward: many llm* commands (llmload, llmkvprec, llmmaxcontext) are engine-only and must vanish or error cleanly in remote-only builds

## Open questions
- Wire direction for remote generation: extend System_UartLink with firmware-initiated framed messages (breaks the strict request/response discipline the other slice owns), or have the CM5 poll a new `llmpending`-style command for queued prompts and push results back via a new command? The result-buffer seam composes with either, but latency and framing differ.
- Flag architecture decision: is there flash headroom to just enable ENABLE_ONDEVICE_LLM on the XIAO build (engine + esp-dsp code size unmeasured against the ~1.3MB factory headroom), making Option A cheap — or is the Option C split required? Needs a trial build.
- Should the remote path bypass llmFramePrompt entirely (send raw user text + a CM5-side system prompt), and should chatBeginTurn also ship recent ring turns to the CM5 for true multi-turn context (the ring already holds raw user text — the data is there, just never transmitted)?
- Response length budget for remote: keep 8KB result buffer / 2048B turn cap, or raise for CM5-scale answers? G2 (180B tail) and OLED cope either way, but the web turns endpoint and `llmturns` pagination assume ≤2KB turns.
- How should llmstatus/LLMState represent a remote backend (new REMOTE state vs. synthetic READY), and what happens to engine-only commands (llmload, llmkvprec, llmmaxcontext, llmcorrupttest) when backend=remote?
- Streaming granularity over 921600-baud UART: token-by-token push gives the live-typing UX the surfaces are built for (drain handles arbitrary chunk sizes), but each fragment needs framing — does the link protocol slice's design allow multi-line/partial-response frames, and does the 2047B inbound line cap force chunked result pushes?
- Concurrency with STT: the engine contract enforces one generation in flight (done flag + chat mutex) — is one-at-a-time acceptable for the combined STT+LLM CM5 service, or does the planner need parallel sessions (which the session-id demux does NOT support today)?
