# llmResearch

## Summary
LLM inference on Pi 5/CM5 (4x Cortex-A76 @2.4GHz, LPDDR4X-4267, no GPU) is viable for voice-query answering only in the 0.5B-3B Q4 tier, and generation is memory-bandwidth-bound while prefill is compute-bound — the two must be budgeted separately. Cross-source consensus at Q4_K_M: 1B-class models generate 10-21 tok/s (Llama 3.2 1B ~17, Qwen3-0.6B ~21, Gemma 3 1B ~10-11 via Ollama), 1.5-2B-class 8-14 tok/s (Qwen2.5-1.5B ~13.8, Gemma 2 2B ~8-11), 3-4B-class 3.5-9 tok/s (Llama 3.2 3B measured 4.88 by Geerling with llama.cpp CPU-only at 11.9W, up to 8.8 in the most optimistic source; Phi-3.5-mini 3.4-7.4), and 7-8B at 2-3 tok/s (batch-only, not interactive). Prefill runs only ~4-5x generation speed on this CPU: ~62-110 tok/s for 0.5-1.5B models, ~33-51 tok/s for 2-4B. That makes prefill the TTFT killer: a 300-token system prompt on a 1.5B model costs ~5s before the first token. The fix is llama-server's KV-prefix caching (cache_prompt is default-on, plus --cache-reuse): with a static system prefix cached, per-turn prefill is only the STT transcript (~15-40 tokens ≈ 0.3-0.7s), making <2s first-token latency achievable. Note llama.cpp's ARM Q4_0 runtime-repack (DOTPROD path, ~40% prefill gain; A76 has dotprod, not i8mm) had a history of not firing in llama-server (ggml issue #12701) — verify AARCH64_REPACK=1 in server logs on the deployed build.

Serving-shape comparison for one long-lived "AI service" hosting both STT and LLM: (a) llama-server as a supervised subprocess spoken to over localhost HTTP is the strongest option — no Python in the hot path, default prompt caching, /health endpoint, slot save/restore, crash isolation from the STT engine, and mmap'd weights mean the OS page cache keeps restarts warm (weights are not re-read from disk if the process bounces). (b) llama-cpp-python in-process carries a measured 12-18% latency overhead, a logits_all footgun, upstream version lag, and long-running memory-leak reports — poor fit for an always-on daemon that also runs STT threads under the GIL. (c) Ollama is 10-20% slower than raw llama.cpp (worst at prefill: 80 vs 108 tok/s on the same model) and its default keep_alive=5m silently unloads the model, adding a multi-second cold reload after idle — usable only with OLLAMA_KEEP_ALIVE=-1 and accepted overhead. Core allocation: the voice pipeline is naturally sequential (record → STT → LLM), so each phase can use all 4 threads; true concurrency only arises if STT streams while the LLM prefills, in which case split 2+2 (or 3 LLM / 1 STT) — running both saturated on 4 cores roughly halves each. whisper.cpp tiny/base are the only real-time STT options on this CPU (base ≈ real-time at 4 threads, small is 0.4-0.6x RT), and tiny/base fit in <1GB.

Thermals are a hard carrier-board constraint: a bare CM5 begins throttling 15-28s into sustained all-core load, drops to 1.5GHz (≈ -40% tok/s); a passive heatsink delays throttle to ~11-12 min; active cooling holds ~58°C indefinitely over 2h sustained inference. Sustained-generation power is 7.4-11.9W SoC-side, so budget ~15W and a fan (or a large chassis-coupled heatsink) on the carrier. RAM fit at Q4 with whisper tiny/base (+~0.5GB) and OS (~0.8GB) co-resident: 4GB CM5 → 0.5-1.7B comfortably, 2B tight; 8GB → anything through 4B with full headroom (recommended SKU); 16GB → enables 7-8B but they are too slow to matter interactively. KV cache is a non-issue at voice scale: computed from published model configs, Llama 3.2 1B costs ~32KB/token f16 (~64MB @2048 ctx) and Qwen2.5-1.5B ~29KB/token (~57MB @2048); a short voice exchange needs only 1-2K context, so tens of MB.

PRIMARY RECOMMENDATION: Qwen2.5-1.5B-Instruct Q4_K_M (also produce a Q4_0 variant and bench the ARM-repack prefill delta) served by llama-server (-t 4, -c 2048, --cache-reuse 256, single slot) as a supervised subprocess of the AI service, on an 8GB CM5 with active cooling; whisper.cpp base (or tiny for speed) in the same service, phases run sequentially. Expected budget per exchange after STT: ~0.3-0.7s prefill of the transcript against a cached system prefix + first tokens streaming at ~13-14 tok/s — inside the <2s first-token goal with margin. Fallback for a 4GB SKU: Qwen3-0.6B (21 tok/s, <1.3GB) with thinking mode disabled. Step-up if quality demands it: Gemma 2 2B or Qwen2.5-3B, accepting ~5-9 tok/s generation and roughly doubled prefill cost. Firmware-side note for the planner: the UART link caps replies at 4095 bytes framed OK:/Error: (System_UartLink.cpp:102-109), so LLM answers relayed to the XIAO must be length-bounded or chunked at the protocol level, and the 2047-byte command-line cap (System_UartLink.cpp:61) bounds any XIAO→CM5 prompt text per line.

- llama-server features for an always-on daemon: cache_prompt is enabled by default (reuses KV from previous request for common prefixes); --cache-reuse N enables chunked KV reuse; -np parallel slots; -t/-tb thread controls; --mlock pins weights; mmap is the default load mode so OS page cache keeps weights warm across process restarts; slot save/restore endpoints (/slots/{id}?action=save|restore) can persist KV to disk; GET /health for supervision; OpenAI-compatible /v1/chat/completions. — https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md:
- KV-prefix caching collapses TTFT on repeated system prompts: llama-server reuses cached KV for the shared prefix and processes only new tokens; reported first-token latency drops from ~400ms to <50ms on repeated prefixes (GPU case), and the Prompt Cache paper measured up to 60x TTFT improvement for CPU inference — on Pi-class prefill (~62 tok/s at 1.5B) caching a 300-token system prompt saves ~5s per turn. — https://github.com/ggml-org/llama.cpp/discussions/13606:
- llama-cpp-python measured 12-18% latency overhead vs native llama.cpp server (median TTFT 450ms vs 380ms same hardware); logits_all=true default historically tanked performance; multiple open reports of memory not being released in long-running use; wrapper version lags upstream llama.cpp releases. — https://github.com/abetlen/llama-cpp-python/issues/398:
- Ollama default keep_alive is 5 minutes: the model is silently unloaded after idle and the next request pays a 3-30s cold reload (long end on SD/eMMC-class storage). OLLAMA_KEEP_ALIVE=-1 (or 24h) is mandatory for an always-on assistant. Ollama also maintains its own model store and Go daemon — a second service to supervise. — https://mljourney.com/ollama-keep-alive-and-model-preloading-eliminate-cold-start-latency/:
- whisper.cpp on Pi 5 (4 threads): tiny processes an utterance in ~2-3s and runs comfortably faster than real-time; base is ~real-time to 2x with -t 4 (~30% better accuracy than tiny); small is 0.4-0.6x real-time — too slow for live mic use. tiny and base fit in <1GB RAM; small needs ~2GB. — https://www.promptquorum.com/power-local-llm/local-whisper-stt-comparison-2026:
- whisper.cpp and llama.cpp share the same GGML foundation and are proven to coexist in one process/pipeline (talk-llama example in the whisper.cpp repo hosts both engines with per-engine thread counts); no Python needed in the hot path. — https://github.com/ggml-org/whisper.cpp/blob/master/examples/talk-llama/README.md:
- CM5 thermals: bare board begins throttling 15s into sustained all-core load, reaching the 1.5GHz floor by 28s; threshold 80-85C; passive heatsink alone delays throttle to ~11m20s (case+heatsink 12m29s); dedicated CM5 heatsink runs 22C cooler than a universal block and 38C cooler than bare. - CM5 active-cooler coverage corroborated: Raspberry Pi's own CM5 cooler exists because the module 'really needs' it under sustained load; third-party tests agree passive is fine only for light/intermittent workloads. — https://www.tomshardware.com/raspberry-pi/raspberry-pi-compute-module-5-receives-the-active-cooler-that-it-really-needs:
- KV cache sizing (computed from published model architecture configs, f16 KV, not web-measured): Llama 3.2 1B (16 layers, 8 KV heads, d=64) = ~32KB/token → ~64MB at 2048 ctx; Qwen2.5-1.5B (28 layers, 2 KV heads GQA, d=128) = ~29KB/token → ~57MB at 2048 ctx. A short voice exchange (system prefix + query + answer) needs 1-2K context, so KV is tens of MB — negligible next to weights on any SKU.
- Generation is memory-bandwidth-bound (computed sanity check): Pi 5/CM5 LPDDR4X-4267 gives ~17GB/s theoretical; dividing by Q4 weight size predicts ceilings of ~24 tok/s @0.7GB (1B) and ~8-9 tok/s @2.1GB (3B), matching measured 17-21 and 4.9-8.8 — so faster clocks/cooling help prefill, but generation cannot exceed this ceiling regardless of thermal headroom.
- Firmware link bounds (verified in working tree): inbound command line cap 2047 bytes (kUartLineCap, over-long lines discarded whole) — components/hardwareone/System_UartLink.cpp:61
- Firmware link bounds: one 4095-byte reply outbound per command; RX/TX ring buffers 4096 bytes at 921600 baud — any LLM answer relayed to the XIAO must fit 4095B per exchange or be chunked by protocol design — components/hardwareone/System_UartLink.cpp:102
- Firmware reply path sets outputMask=MSG_ROUTE_FILE so only the command's own result crosses the wire (no debug/broadcast leakage), executed via submitAndExecuteSync — components/hardwareone/System_UartLink.cpp:281

## Constraints
- 4 Cortex-A76 cores total, no GPU/NPU: llama.cpp generation saturates at 4 threads; STT and LLM running truly concurrently roughly halve each other — pipeline them sequentially, or split 3/1 or 2/2 only during deliberate overlap (e.g., streaming STT while LLM prefills)
- Generation speed is memory-bandwidth-capped (~17GB/s LPDDR4X shared by CPU): ~24 tok/s absolute ceiling for 1B Q4, ~9 tok/s for 3B Q4 — no software tuning raises this; model size choice IS the latency choice
- Prefill is only 4-5x generation speed (30-110 tok/s): every turn's TTFT = prompt_tokens/prefill_rate; a static system prompt MUST be KV-cached (llama-server cache_prompt/--cache-reuse) or the <2s first-token goal is unreachable for prompts >100 tokens
- Bare CM5 throttles to 1.5GHz within 15-28s of sustained all-core load (~-40% clock); the carrier board must provide active cooling or an oversized coupled heatsink; budget ~12-15W for the SoC under sustained generation (measured 7.4-11.9W)
- RAM fit at Q4 with whisper tiny/base (+~0.5GB) and OS (~0.8GB) co-resident: 4GB CM5 = 0.5-1.7B models only; 8GB = up to 4B comfortably; 16GB = 7-8B loadable but 2-3 tok/s makes them non-interactive
- Ollama's default keep_alive=5m unloads the model after idle (3-30s cold reload); any Ollama deployment needs OLLAMA_KEEP_ALIVE=-1
- Cortex-A76 supports dotprod but NOT i8mm: use Q4_0-repack-eligible quants for prefill speed; verify llama-server actually performs runtime repack (historical issue #12701)
- UART link protocol bounds (firmware, verified): 2047B max inbound command line, 4095B max reply, OK:/Error: framing — CM5-side LLM answers must be length-bounded or chunked to fit (components/hardwareone/System_UartLink.cpp:61,102)
- Whisper small is not real-time on this CPU: STT engine choice is whisper.cpp tiny or base only for live voice

## Options
### llama-server subprocess + localhost HTTP (RECOMMENDED serving shape)
The AI service (any language) supervises a llama-server child process and calls its OpenAI-compatible API on 127.0.0.1; whisper.cpp runs in-process or as a library in the AI service. Configure: -t 4 -c 2048 --cache-reuse 256, single slot, optional --mlock.
Pros: No Python in the LLM hot path; fastest prefill of the three; cache_prompt on by default + --cache-reuse → per-turn prefill is just the transcript (~0.3-0.7s); Crash isolation: an LLM assert cannot take down the STT/UART side; /health enables supervision and restart; mmap default means the OS page cache keeps weights warm across restarts — warm restart in ~1s, and a future second consumer process would share the same physical pages; Slot save/restore can persist conversation KV across service restarts if ever needed
Cons: One extra process to supervise and version; Localhost HTTP adds ~1-5ms per call (negligible at these token rates); Must verify ARM Q4_0 runtime repack fires in the server path (issue #12701 history)
### In-process llama-cpp-python (or direct libllama linkage)
Single binary/daemon embeds both whisper and llama via bindings; Python orchestration typical.
Pros: One process, one deployment unit; Direct per-token callbacks without HTTP streaming; Direct C linkage (talk-llama pattern, C++) avoids Python entirely and is the leanest possible footprint if the team accepts C++
Cons: Python wrapper: measured 12-18% latency overhead, logits_all footgun, upstream version lag, long-running memory-leak reports — bad daemon citizen; GIL contention between STT threads, UART handling, and token callbacks; No crash isolation: a ggml abort kills STT and the UART link too; Prompt caching must be reimplemented by hand (llama_state APIs) instead of inherited from llama-server
### Ollama daemon
Stock Ollama service; AI service calls its REST API.
Pros: Trivial setup and model management on ARM (one command); Well-trodden on Pi 5; most published Pi benchmarks use it
Cons: 10-20% slower than raw llama.cpp overall, worst at prefill (80 vs 108 tok/s same model) — directly attacks the TTFT budget; Default keep_alive=5m unloads the model; needs OLLAMA_KEEP_ALIVE=-1; Less control over thread pinning, quant repack, and ubatch tuning; A second Go daemon plus its own model store on a constrained device
### Model choice: Qwen2.5-1.5B-Instruct Q4_K_M (PRIMARY)
13.8 tok/s gen / 62 tok/s prefill / 1.1GB on Pi 5 8GB; strongest quality-per-token-rate in the 1.5B tier per multiple sources ('Qwen models stand out as the most effective overall').
Pros: Meets <2s TTFT with cached system prefix: 15-40 transcript tokens ≈ 0.3-0.7s prefill + streaming at ~14 tok/s; Fits 4GB SKU alongside whisper base (1.1+0.5+0.8 ≈ 2.4GB); Also bench a Q4_0 build for the ~40% ARM-repack prefill gain
Cons: Quality below 3B-class for complex queries; Qwen2.5 era — check whether a Qwen3-1.7B (1.4GB Q4) non-thinking config benches competitively on the real hardware, since published Pi numbers for it are missing
### Model fallback/step-up alternatives
4GB-SKU floor: Qwen3-0.6B (21 tok/s, <1.3GB, disable thinking mode). Speed pick: Llama 3.2 1B (17.2 tok/s / 76 prefill / 0.9GB), weaker instruction quality. Quality step-up on 8GB: Gemma 2 2B (8-11 tok/s) or Qwen2.5-3B / Llama 3.2 3B (4.9-8.8 tok/s) — accepts ~2x prefill cost and generation at the edge of conversational; Phi-3.5-mini 3.8B (3.4-7.4 tok/s) is the ceiling and marginal.
Pros: Covers all three CM5 RAM SKUs with a concrete ladder; All are single-file GGUFs swappable behind the same llama-server flag
Cons: 3B+ tier risks blowing the 2s first-token budget once answers stream slowly (a 60-token answer takes 7-12s to finish at 5-9 tok/s); Gemma models have larger KV/embedding overhead per parameter; Gemma 3 Ollama numbers underperform same-size Llama/Qwen

## Open questions
- Does the current llama-server build perform Q4_0 runtime repack (AARCH64_REPACK) on Cortex-A76, or does issue #12701 still bite? Check server startup logs on the Pi and bench Q4_0 vs Q4_K_M prefill before committing to a quant.
- Qwen3-1.7B has no credible published Pi 5 tok/s; it would be the natural quality upgrade over Qwen2.5-1.5B at only +0.3GB — needs an on-device llama-bench run (with thinking mode disabled) to decide.
- Phi-4-mini (3.8B) Pi 5 measurements were not found anywhere; only Phi-3.5-mini numbers exist (3.4-7.4 tok/s). Treat Phi-4-mini as unmeasured.
- Benchmark spread is ~2x between sources for identical model/quant (Geerling 4.88 vs localaimaster 8.8 tok/s on Llama 3.2 3B) — build flags, quant variant, and cooling dominate; final model selection must come from llama-bench on the actual CM5 + carrier thermal solution, not from these published numbers.
- Will STT stream partial transcripts so LLM prefill can overlap the tail of speech (hides most of the 0.3-0.7s prefill)? If yes, core split during overlap (2+2 vs 3+1) needs a measurement; if the pipeline stays strictly sequential, both engines can use all 4 threads and no split policy is needed.
- Which CM5 SKU is the target? 8GB is the recommendation (full model ladder + headroom); 4GB forces the 0.6-1.7B tier; 16GB buys nothing interactive.
- Carrier thermal design: is a fan acceptable, or must the enclosure passively sink ~12W? Passive-only caps sustained generation at ~11-12 min before a ~40% clock drop.
- How should >4095-byte LLM answers be handled over the UART link — truncate with a marker, paginate via repeated commands, or add a chunked-reply opcode? (Protocol design decision, firmware cap verified at components/hardwareone/System_UartLink.cpp:102.)
- TTS was out of scope for this slice: if the CM5 must also speak (Piper etc.), its CPU/RAM budget changes the core-allocation answer and should be sized before the process model is frozen.
