## Summary
STT engine menu for Pi 5/CM5 (4x A76 @2.4GHz, no accelerator), August 2026. The field splits into three tiers. (1) Streaming-native small models — sherpa-onnx streaming Zipformer (transducer, int8 ~68MB English model, Apache-2.0, pip aarch64 wheels, built-in endpoint rules), Moonshine v2 (33M/123M/245M params, MIT, pip `moonshine-voice`, position-free streaming encoder with published Pi-5 post-utterance latencies of 237/527/802 ms for tiny/small/medium), and Vosk (Kaldi-era, 40MB small-en model, ~300MB runtime, true word-by-word streaming, but worst accuracy tier: 9.85 WER librispeech small vs Moonshine v2 small 2.49 clean). (2) Whisper-family batch engines — whisper.cpp (MIT, C lib, now with built-in Silero VAD v6.2.0 via --vad; on Pi 5 tiny.en runs comfortably faster than realtime, base.en ≈realtime at -t 4, small ~0.4-0.6x realtime; q5_0 quant recommended; RAM ~1GB tiny/base) and faster-whisper/CTranslate2 (MIT, real aarch64 PyPI wheels, CPU-only on arm64, int8; tiny ≈2-3s per utterance on Pi 5; roughly comparable to whisper.cpp on ARM, with whisper.cpp usually the lighter embedded choice). (3) New 0.6B-class high-accuracy models — NVIDIA Parakeet TDT 0.6b v3 (6.34% avg WER, beats Whisper large-v3's ~7.4%, OpenMDW license, int8 ONNX 632-650MB, runs in-process via `onnx-asr` pip or sherpa-onnx; RTF 0.01-0.02 on i7-12700K but NO published Pi-5 numbers — plausibly RTF 0.1-0.4 on A76, must be benched) and NVIDIA Nemotron Speech Streaming 0.6B (Apr 2026, cache-aware conformer transducer, int4 0.67GB, 8.20% WER streaming, 0.56s algorithmic delay — but distributed via Microsoft Foundry Local/ONNX Runtime GenAI, benched only on 32-core EPYC; packaging on Pi is unproven). Qwen3-ASR-1.7B is below realtime on CPU per the Nemotron paper — excluded.

All serious candidates run as long-lived in-process components: faster-whisper, Vosk, sherpa-onnx, Moonshine, and onnx-asr are pip-importable Python libs holding the model resident; whisper.cpp is a C library (libwhisper) linkable into a C++ service (community pywhispercpp for Python). None require subprocess isolation, though whisper.cpp is often run as its own server binary. Every recommended engine consumes exactly the payload the XIAO produces (16kHz/16-bit mono PCM). VAD/endpointing: silero-vad is the default (~2MB, <1ms per 32ms chunk on CPU, MIT, ONNX, LSTM state carried across chunks — ideal for weak mic-side endpointing); TEN-VAD (pip `ten-vad`) claims better precision and ~32% lower RTF than Silero; sherpa-onnx has rule-based endpointing built into its streaming decoder (rule2 trailing-silence default 1.2s), and whisper.cpp now embeds Silero natively.

Concurrency with llama.cpp is the binding constraint: a 3B Q4 model yields 4-7 tok/s only when llama.cpp owns all 4 cores. Realistic split: pin STT to 1-2 onnxruntime intra-op threads. Streaming engines with RTF≈0.1-0.3 (Zipformer int8, Moonshine tiny/small, Vosk small) absorb this easily — they decode during speech and during the UART transfer window (921600 baud ≈ 92KB/s ≈ 2.9x realtime for 32KB/s PCM, so a 5s utterance takes ~1.7s to transfer, free overlap time), delivering the final transcript within roughly the endpoint-silence timeout (0.3-1.2s) after end of speech. Batch engines (whisper.cpp/faster-whisper) pay transfer + full inference serially: ~1-2s (tiny.en) to ~4-6s (base.en at 2 threads) for a 3-5s utterance, worse under LLM contention. RAM: on a 4GB CM5 with a ~2-2.5GB resident 3B LLM, the STT budget is ~1GB — which excludes Parakeet-class (needs ~1.5-2GB runtime) and whisper small+, but fits Zipformer int8 (~200-400MB), Moonshine tiny/small (<500MB), Vosk small (~300MB), whisper.cpp tiny/base q5_0 (~1GB).

RECOMMENDATION for this use case (English-first utterances over UART, concurrent LLM): PRIMARY = Moonshine v2 small via `moonshine-voice` (MIT, in-process Python, best accuracy-per-FLOP with the only vendor-published Pi-5 latency numbers — 527ms post-utterance; add silero-vad for endpointing since Moonshine has no built-in endpointer), with Moonshine v2 tiny as the degrade step when the LLM is generating. FALLBACK = sherpa-onnx streaming Zipformer en int8 (Apache-2.0, C++ or Python in-process, built-in endpointing, smallest RAM, most mature aarch64 packaging, trivially thread-capped) — also the right base if the service ends up C++ rather than Python. Keep whisper.cpp base.en-q5_0 (+built-in Silero VAD) as the robustness/accuracy escape hatch for noisy audio, and bench Parakeet TDT int8 on-device before ruling it in for an 8GB CM5. Both primary and fallback claims about concurrent-load latency are extrapolations — a 2-thread-capped on-device bench while llama.cpp decodes is the single most important validation task.

## Key facts
- whisper.cpp on Pi 5: tiny runs comfortably faster than realtime, base ~realtime with -t 4 (4 threads), small only 0.4-0.6x realtime; q5_0 GGML quant recommended; RAM ~1GB for tiny/base, ~2GB small; all inference is ARM NEON CPU — https://www.promptquorum.com/power-local-llm/local-whisper-stt-comparison-2026:
- whisper.cpp has built-in Silero VAD support (issue #3003 merged 2025, upgraded to Silero v6.2.0 Nov 2025 via PR #3524): VAD segments extracted first, only speech passed to Whisper; models fetched via models/download-vad-model.sh — https://github.com/ggml-org/whisper.cpp/issues/3003:
- whisper.cpp streaming is a sliding-window hack, not a streaming architecture: examples/stream re-transcribes ~every 500ms with a context window plus a 'very basic' VAD mode; usable but re-decodes audio repeatedly, costly under CPU contention — https://github.com/ggml-org/whisper.cpp/tree/master/examples/stream:
- whisper.cpp audio_ctx optimization cuts JFK-clip tiny-f32 transcription from ~9s to ~3s on Pi-class hardware — https://openbenchmarking.org/performance/test/pts/whisper-cpp/bba40be5b54aebfa2f7be27b6d5384dadef5d6d0:
- faster-whisper/CTranslate2 ships official CPU-only aarch64 manylinux wheels on PyPI (backends: oneDNN, OpenBLAS, Ruy); int8 quantization supported; ~4x faster than openai/whisper reference at same accuracy; MIT license — https://opennmt.net/CTranslate2/installation.html:
- ACM/IEEE SEC Dec-2025 paper 'Performance Evaluation of Whisper-Series Speech Transcription Models on Raspberry Pi' concludes faster-whisper tiny.en/base.en are the Pi-deployable models and Pi 5 (4GB) is the best cost-performance platform (full text paywalled, 403) — https://dl.acm.org/doi/10.1145/3769102.3774244:
- faster-whisper tiny on Pi 5 8GB: ~2-3s to process a spoken command entirely on-device — https://fast.io/resources/openclaw-raspberry-pi-speech-recognition-offline-voice-agent/:
- Vosk: small-en-us-0.15 is 40MB on disk, 9.85 WER librispeech; en-us-0.22-lgraph 128MB, 7.82 WER; en-us-0.22 1.8GB, 5.69 WER; ~300MB runtime RAM for small; Apache-2.0 lib+official models; ~40 languages; true incremental word-by-word streaming via pip vosk in-process; no new model generation 2024-2026 — accuracy tier is now the worst of the field — https://alphacephei.com/vosk/models:
- sherpa-onnx streaming Zipformer transducer en-2023-06-26: 68MB int8, docs report RTF 0.062-0.077 (platform for these RTFs not stated in docs — assume desktop x86; Pi 5 likely 2-4x worse, must bench); Chinese/Korean/bilingual variants exist; Apache-2.0 — https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html:
- sherpa-onnx publishes manylinux2014_aarch64 pip wheels, depends only on onnxruntime, offers Python/C/C++ in-process APIs, and has built-in rule-based endpointing on the streaming decoder (rule1 unconditional silence 2.4s, rule2 trailing-silence-after-speech default 1.2s, rule3 min utterance length) — no external VAD needed — https://k2-fsa.github.io/sherpa/python/streaming_asr/endpointing.html:
- Moonshine v2 (arXiv 2602.12241): tiny 33.6M / small 123.4M / medium 244.9M params; 'ergodic' position-free streaming encoder (sliding-window attention, 16 past frames, ~80ms bounded lookahead, TTFT independent of utterance length); avg open-ASR WER 12.01/7.84/6.65; LibriSpeech-clean 4.49/2.49/2.08; paper benches only Apple M3 (50/148/258ms) and covers English only — https://arxiv.org/html/2602.12241v1:
- Moonshine repo publishes Raspberry Pi 5 streaming-model latencies: Tiny 237ms, Small 527ms, Medium 802ms (post-utterance response latency); MIT license; pip `moonshine-voice` runs in-process on ONNX Runtime; KV-cached incremental processing; repo lists 8 STT languages (English, Spanish, Mandarin, Japanese, Korean, Vietnamese, Ukrainian, Arabic) — vs English-only in the v2 paper, so multilingual is likely a separate/newer model set — https://github.com/usefulsensors/moonshine:
- NVIDIA Parakeet TDT 0.6b v3 (Jan 2026 English, Jun 2026 40-locale multilingual): 6.34% avg WER on Open ASR leaderboard vs ~7.4% Whisper large-v3; int8 ONNX 632-650MB; OpenMDW license; RTF 0.01-0.02 on i7-12700K CPU; runnable in-process via pip `onnx-asr` or sherpa-onnx (arm64-v8a builds exist); no published Pi-5/A76 RTF anywhere — https://huggingface.co/istupakov/parakeet-tdt-0.6b-v3-onnx:
- NVIDIA Nemotron Speech Streaming 0.6B (arXiv 2604.14493, Apr 2026): cache-aware conformer transducer, int4 0.67GB, 8.20% avg WER in true streaming, 0.56s algorithmic delay, 7.2x realtime — but on 32-core EPYC; distributed via Microsoft Foundry Local / ONNX Runtime GenAI SDK; same paper: Parakeet degrades to 12.83% WER when chunk-streamed, Qwen3-ASR-1.7B is sub-realtime on CPU (RTFx 0.49) — https://arxiv.org/html/2604.14493v2:
- silero-vad: ~1-2MB model, processes 32ms chunks (512 samples @16kHz) in <1ms on CPU, speech probability per chunk with LSTM state carried across chunks, ONNX runtime, MIT — the standard endpointing choice for weak mic-side endpointing — https://github.com/snakers4/silero-vad:
- TEN VAD (pip `ten-vad`): claims higher precision than both WebRTC-VAD and Silero on librispeech/gigaspeech/DNS-Challenge testsets and ~32% lower RTF than Silero; ONNX, runs on Linux aarch64 — credible newer alternative, license terms need verification before adoption — https://huggingface.co/TEN-framework/ten-vad:
- llama.cpp on Pi 5: 3B Q4_K_M generates ~4-7 tok/s using all 4 cores (Llama-3.2-3B 4-6 tok/s w/ OpenBLAS, up to 8.8 reported); 7B Q4 0.7-3 tok/s; 8GB Pi recommended for 3B — the LLM will want every core whenever it is decoding — https://localaimaster.com/blog/llm-raspberry-pi-5:
- In-process integration map: faster-whisper (Python lib), Vosk (Python lib wrapping libvosk), sherpa-onnx (Python + C/C++ API), moonshine-voice (Python lib), onnx-asr (Python lib) all hold models resident in the service process; whisper.cpp is a C library requiring C++ linkage or the community pywhispercpp binding — none require a subprocess model, so a single long-lived 'AI service' process holding both STT and llama.cpp contexts is feasible with every candidate — https://pypi.org/project/sherpa-onnx/:
- UART transfer arithmetic (from task context, not web): 921600 baud ≈ 92KB/s vs 32KB/s for 16kHz/16-bit mono PCM = ~2.9x realtime, so a 5s utterance needs ~1.7s wire time; streaming engines can decode during transfer, batch engines add it to end-to-end latency — docs/UART_HOST_LINK_PLAN.md:

## Constraints
- 4 shared Cortex-A76 cores: llama.cpp needs all 4 for its 4-7 tok/s on 3B Q4, so STT must be capped at 1-2 intra-op threads (all candidate runtimes support this) or the pipeline must serialize STT-then-LLM per interaction; concurrent-load STT latency will be ~1.5-2x the solo numbers
- RAM on 4GB CM5: ~2-2.5GB resident for a 3B Q4 LLM + OS leaves ~1GB for STT — this excludes Parakeet/Nemotron 0.6B-class (~1.5-2GB runtime) and whisper small/medium; they only become viable on the 8GB variant
- No GPU/NPU: everything is NEON CPU; CTranslate2 arm64 wheels are CPU-only; no CUDA path exists
- Input format is fixed by firmware: 16kHz/16-bit mono PCM utterances — all recommended engines accept this natively, no resampling stage needed
- UART wire speed (921600 baud ≈ 2.9x realtime for 16kHz PCM) means audio arrival is itself streamed over ~1/3 of utterance duration; batch engines cannot start until the last byte arrives unless the link protocol streams PCM incrementally
- License floor is met everywhere that matters: whisper.cpp MIT, faster-whisper MIT, Vosk Apache-2.0, sherpa-onnx Apache-2.0, Moonshine MIT, Parakeet OpenMDW, silero-vad MIT — no copyleft contamination risk in the AI service
- English-first today, but if multilingual becomes a requirement the menu narrows: Vosk (40 langs, old accuracy), whisper family (99 langs), Parakeet v3 multilingual (40 locales, RAM-heavy), Moonshine multilingual (8 langs, unverified on Pi)
- Whisper-family 'streaming' is fake (sliding-window re-decode) — real streaming with bounded lookahead exists only in Zipformer transducers, Moonshine v2, and Nemotron 0.6B

## Options
### PRIMARY: Moonshine v2 small (moonshine-voice, in-process Python) + silero-vad endpointing
123M-param MIT streaming model, pip-installed, ONNX Runtime backend; the only engine with vendor-published Pi 5 latency (527ms post-utterance for small, 237ms tiny); decode overlaps UART transfer via KV-cached incremental processing; degrade to tiny while LLM is generating.
Pros: Best accuracy-per-compute in the field (2.49 WER LibriSpeech-clean at 123M params — beats whisper base/small); Real streaming encoder, TTFT independent of utterance length, ~80ms lookahead; Pi-5-measured latencies exist; MIT; trivial pip packaging; in-process; Thread count controllable via onnxruntime session options for LLM coexistence
Cons: No built-in endpointing — must pair with silero-vad (cheap: <1ms/32ms chunk); English-only in the v2 paper; multilingual variants unverified on Pi; Younger ecosystem than whisper; repo/package naming in flux (usefulsensors → moonshine-ai); Concurrent-with-llama.cpp behavior unbenchmarked
### FALLBACK: sherpa-onnx streaming Zipformer en int8 (in-process, Python or C++)
68MB int8 transducer, Apache-2.0, manylinux2014_aarch64 pip wheels, built-in rule-based endpointing (trailing-silence 1.2s default), incremental decoding during speech and UART transfer; final transcript ≈ endpoint timeout after end of speech.
Pros: Smallest RAM (~200-400MB) — safest on 4GB alongside the LLM; Endpointing built into the decoder — no separate VAD plumbing; Most mature aarch64 packaging of the field; C++ API if the AI service ends up non-Python; RTF low enough (0.06-0.08 desktop; expect ~0.15-0.3 Pi) to run capped at 1-2 threads
Cons: English model dates to 2023-06; accuracy below Moonshine v2 small and whisper base on hard audio; Docs' RTF platform unstated — Pi 5 numbers must be measured; k2-fsa model zoo navigation and config surface is fiddly
### Robustness escape hatch: whisper.cpp base.en q5_0 with built-in Silero VAD
Batch (utterance-mode) transcription in a C library; ~realtime at 4 threads on Pi 5, ~half that at 2 threads; VAD integrated natively since 2025 (--vad, Silero v6.2.0).
Pros: Best robustness on noisy/accented/far-field audio in this weight class; huge community; MIT; single C binary or linkable lib — fits a C++ service directly; Built-in Silero VAD trims silence before decode; Whisper accuracy tier with multilingual option (drop .en) already packaged
Cons: Batch-only: 3-5s utterance costs ~3-6s at contended 2 threads — worst interactive latency; Sliding-window 'streaming' re-decodes constantly, hostile to a busy LLM core budget; RAM ~1GB for base — tight but OK on 4GB
### faster-whisper tiny/base int8 (in-process Python)
CTranslate2 aarch64 CPU wheels, int8; tiny ~2-3s per utterance on Pi 5.
Pros: Simplest Python integration if the AI service is Python anyway; int8 memory reduction; MIT; Roughly whisper.cpp-class speed on ARM
Cons: Batch-only, same latency profile as whisper.cpp without the C-level footprint control; On ARM specifically, whisper.cpp is generally the lighter and better-tuned choice — faster-whisper's edge is x86; Python+CTranslate2 runtime overhead vs a 68MB zipformer
### Vosk small-en (minimal floor)
40MB Kaldi model, ~300MB runtime, true word-level streaming, Apache-2.0.
Pros: Lowest resource floor; runs even on Pi Zero; Genuine incremental partial results with per-word timing; 40+ languages via drop-in model swap
Cons: Worst accuracy of the menu (9.85 WER librispeech small) — noticeably poor on open-vocabulary speech; Model generation stale (no 2024-2026 refresh); project momentum is behind sherpa-onnx; lgraph/full models that fix accuracy blow the RAM/latency budget
### Parakeet TDT 0.6b v3 int8 via onnx-asr (8GB-only, bench-gated)
Whisper-large-v3-beating accuracy (6.34% avg WER) in a 650MB int8 ONNX, OpenMDW, in-process via pip onnx-asr or sherpa-onnx.
Pros: Best accuracy available on CPU by a clear margin, incl. 40-locale multilingual v3.5; Very fast per-FLOP (TDT decoder skips blank frames): RTF 0.01-0.02 on desktop CPU
Cons: Zero published Pi-5/A76 benchmarks — RTF on 2 threads could be 0.3-1.0, unknown; ~1.5-2GB runtime excludes the 4GB CM5 when the LLM is resident; Batch-mode; streaming variant degrades to 12.83% WER per the Nemotron paper

## Open questions
- Actual Pi 5 RTF for sherpa-onnx Zipformer en int8 and for Parakeet TDT int8 at 1-2 threads — no published numbers exist; both need a 30-minute on-device bench before the plan hardens
- STT latency under active llama.cpp decode (the real operating condition): all published numbers are solo-engine; need a bench of Moonshine v2 small capped at 2 threads while llama.cpp 3B Q4 decodes on 4
- Will the UART protocol stream PCM incrementally (enabling streaming engines to decode during transfer) or deliver a complete utterance blob per the current request/response 'OK:/Error:' framing? This decision alone swings end-to-end latency by ~1.7s for a 5s utterance and determines whether streaming architectures pay off
- Moonshine v2 multilingual: the repo lists 8 STT languages but the v2 paper is English-only — which models are actually downloadable, at what sizes, and do the Pi 5 latency numbers hold for them?
- Real-world WER on XIAO-mic audio (PDM mic, possible far-field/noise) vs the clean-benchmark numbers all engines advertise — whisper-family robustness may beat Moonshine/Zipformer more than leaderboards suggest; needs a captured-audio test set from the actual device
- CM5 RAM SKU: 4GB vs 8GB decides whether Parakeet-class accuracy is even on the table and how large the LLM can be — the plan should branch on this early
- moonshine-voice package stability: repo migrated usefulsensors→moonshine-ai during 2026; verify current canonical pip name, version, and that ONNX streaming models (not just batch) are exposed through the pip API
- TEN VAD license terms (unverified) if it is preferred over silero-vad for endpointing
- Nemotron Speech Streaming 0.6B outside Microsoft Foundry Local: are raw ONNX graphs obtainable and runnable via plain onnxruntime on aarch64, or is it locked to the Foundry runtime?
