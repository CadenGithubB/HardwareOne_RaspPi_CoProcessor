# uart

## Summary
The UART link today is a strictly loop-task-owned, newline-framed, request/response text channel. RX: uartLinkTick (components/hardwareone/System_UartLink.cpp:298-349) polls the port from loop(), accumulates into a String capped at 2047 bytes (kUartLineCap, :61) matching ExecReq::line[2048]; an over-long line is discarded whole through its newline (sDiscardingLine, :322-329, :339-345) with a rate-limited nag (one per 2s, :75-80); at most ONE command per loop lap (break at :337). Each command runs via submitAndExecuteSync (:288) which BLOCKS the loop task up to 60s (System_Utils.cpp:5005), so the drain, the UI, and anything else hooked on loop() freeze for the whole execution. TX: exactly three write sites, all on the loop task — uartWriteLine (:68-71), the nag-limited variant (:75-80), and the reply blob write (:290-291). Replies are `blob + '\n'` with no length framing; multi-line replies make '\n' a non-unique terminator (the plan's own client recipe compensates with the `json` whole-document token, docs/UART_HOST_LINK_PLAN.md:286-288). RX/TX driver rings are 4096B each, set before begin (:108-109); no flow control exists, TX always drains at wire rate; HardwareSerial::write returns the requested size unconditionally (components/arduino/cores/esp32/HardwareSerial.cpp:585-588) so drops are undetectable.

Throughput: 8N1 = 10 wire bits/byte. XIAO S3 default 921600 baud = 92,160 B/s; UART_LINK_BAUD_MAX 3,000,000 = 300,000 B/s and 2M = 200,000 B/s are available (System_BuildConfig.h:888-889); classic-ESP32 boards cap at 230,400 = 23,040 B/s. 16kHz/16-bit mono PCM = 32,000 B/s: raw = 34.7% of 921600 (16.0% at 2M) — fits; base64 = 42,667 B/s = 46.3% at 921600 (21.3% at 2M) — fits; a length-prefixed binary frame (512B payload + ~5B header/CRC = 517B per 16ms chunk = 32,313 B/s) = 35.1% at 921600 — fits. On classic boards 32,000 > 23,040: live 16k PCM does NOT fit at any encoding; the feature must be S3-gated or compressed (~4:1 ADPCM = 8,000 B/s would fit at 34.7%). UART is full duplex, so outbound audio and inbound text do not share budget. LLM streamed text is bandwidth-trivial (hundreds of B/s); its real constraint is cadence — inbound unsolicited lines can only arrive as commands, one per loop lap, each paying a full blocking submitAndExecuteSync round trip. Direction matters enormously: XIAO→CM5 audio (the STT direction; PDM mic is on the XIAO, MIC_CLK/DATA GPIO42/41, System_BuildConfig.h:875-876) is the safe direction because Linux buffers deeply; CM5→XIAO continuous audio is NOT safe today — the 4096B RX ring holds only 128ms at 32,000 B/s and the plan itself documents 200ms+ loop stalls (UART_HOST_LINK_PLAN.md:219-221), guaranteeing silent driver-ring overflow.

Interleaving/mux: the HAL serializes individual write() calls with a real per-UART mutex (uartWriteBuf, esp32-hal-uart.c:1229-1237; CONFIG_DISABLE_HAL_LOCKS unset, sdkconfig:628), but every existing TX sequence is TWO write() calls (blob then newline), so any second-task writer can inject bytes between them — and since replies carry no framing at all, a mux must add real framing to REPLIES too, not just to pushed frames. The natural seams: (1) convert all TX to a single frame-writer function around :68-71/:290-291 that builds the complete frame in RAM and issues ONE write() ≤~1-2KB (single-write atomicity via the HAL mutex; frames must stay well under the 4096 TX ring because uart_write_bytes blocks while HOLDING the HAL mutex once the ring is full, stalling other writers for wire time); (2) a loop-task-only pusher hooked inside uartLinkTick beside :313-348 needs zero new locking but inherits every loop stall and the up-to-60s command freeze — unacceptable for glitch-free audio; (3) a cross-task writer (mic-capture task calling the frame writer) is the streaming-grade shape but breaks the current lifecycle model — uartLinkStop/start are loop-task-only via the sPending deferred-request mechanism (:52-53, :302-311), so stop() can free the port under a mid-write task; a link-level TX mutex shared by writers and stop, plus a gUartAuthed/sStarted check per frame, is the minimal fix. Demux at the receiver: text lines never contain 0x00, so COBS/SLIP frames delimited by 0x00 coexist cleanly with newline text; alternatively type-tagged base64 text lines ("AUD <b64>") keep the channel pure-text at 33% bandwidth cost (still fits). A modal per-transfer 'binary mode' is the worst option: desync after a crash leaves the parser wedged, and the channel's recovery story today is precisely that any garbage resyncs at the next newline.

USB: not an option on this carrier, by explicit design. The carrier routes NO USB between CM5 and module — no connector, no pads, no nets (docs/CM5_CARRIER_DESIGN_BRIEF.md:145-154); the rationale is a security invariant: ESP32-S3 native USB can enter ROM download mode with no BOOT strap, while UART cannot, which is why the link is UART-only and the CM5 can never flash the module (:19-23, :193-196). The XIAO's own USB-C carries the USB-Serial-JTAG console today (CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y, sdkconfig:1437; ARDUINO_USB_MODE=1 + CDC_ON_BOOT, sdkconfig:604-605) and is operator-facing (bench console, flashing, the recovery/updater procedures). The S3 has a single USB PHY: switching to TinyUSB OTG would kill the USB-Serial-JTAG console and the established recovery workflow. Conclusion for the planner: the UART link at 921600 (or 2M) is the only XIAO↔CM5 channel, and it has ample bandwidth for one-direction 16k PCM plus text — the engineering work is framing/mux and TX-ownership, not throughput. Session model is streaming-friendly by default (sessionIdleUart=0 never expires; idle clock refreshes only on completed inbound lines, :336) but re-login costs ~12s of PBKDF2 ON the loop task, revocation sweeps clear gUartAuthed asynchronously (pushers must check it per frame), the wizard parks the drain silently (:317), and a chatty link during OTA probation postpones image validation (UART_HOST_LINK_PLAN.md:318-320).

## Constraints
- Newline-framed text only; inbound line ≤2047B (over-length discarded whole, never truncated-and-executed); reply ≤4095B, exactly one delivery per command, no unsolicited TX exists today
- All link RX/TX happens on the loop task; submitAndExecuteSync blocks it up to 60s per command and the repo documents 200ms+ loop stalls — any loop-hooked streamer inherits both
- RX and TX driver rings are 4096B and can only be resized before begin(); 4096B RX = 128ms of headroom at 32,000 B/s, so continuous inbound (CM5→XIAO) 16k PCM WILL drop silently with today's drain
- No flow control (CTS/RTS unwired, reserved GPIO6/7 for a future carrier rev); write() returns success unconditionally — drops are undetectable at the sender
- HAL mutex atomicity is per-write()-call only; every existing TX sequence is two calls (blob+newline), and uart_write_bytes blocks while holding the mutex when the ring fills — mux frames must be single-write and ≤~1-2KB
- Port lifecycle (stop/restart) is loop-task-only via the sPending mechanism; a cross-task writer requires new synchronization against uartLinkStop or it writes into a freed port
- S3 boards: 921600 default / 3M max (2M is the divider-exact rate); classic-ESP32 boards: 230400 max = 23,040 B/s < 32,000 B/s — live 16k PCM must be S3-gated or compressed ~4:1
- No USB data path between CM5 and XIAO exists on the carrier, by security design (S3 native USB = strapless ROM download; the CM5 must never be able to flash the module) — USB as a second channel requires a carrier redesign AND abandoning the flashing-isolation invariant
- S3 single USB PHY: enabling TinyUSB OTG kills the USB-Serial-JTAG console and the established bench/recovery procedures (updater console, cable-flash workflow)
- Auth session (gUartAuthed) is cleared asynchronously by revocation sweeps, uartlink off, and stop; login costs ~12s PBKDF2 on the loop task; brute-force key 'uart'; sessionIdleUart>0 would expire an outbound-only stream because the idle clock stamps only on inbound completed lines
- MSG_ROUTE_FILE-only output mask and captureOutput=false are load-bearing for reply framing — an event-push design must not route through capture or broadcast; the MSG_ROUTE_UART sink option burns the last routing bit and clamps at 255B/line
- Drain parks (dead air) while the setup wizard owns the CLI; a chatty link during OTA probation postpones image validation
- Reply end-of-message is not machine-delimitable today for multi-line replies (internal newlines, no length prefix) — the CM5 client leans on the json token; any mux layer should fix reply framing at the same time

## Options
### A: Loop-task tick pusher (text-tagged base64 frames)
Add an audio/event staging ring (PSRAM) filled by producer tasks; uartLinkTick drains it on the loop task, emitting complete single-write() tagged lines ('AUD <b64>', 'EVT ...') beside the existing drain (seam: System_UartLink.cpp:313-348). No new locking against lifecycle or replies — everything stays on one task.
Pros: Minimal change; preserves the loop-task ownership model and the sPending lifecycle exactly; Pure text channel — CM5 demux is line-prefix dispatch; resync-on-newline recovery story unchanged; base64 16k PCM = 46.3% of 921600 wire — fits with margin
Cons: Starved for the full duration of every command (up to 60s) and every 200ms+ loop stall — audio gaps unless the staging ring covers worst-case stall (6.4KB per 200ms; a 60s command needs 1.9MB or the stream drops); 33% base64 bandwidth tax plus encode CPU on the loop task; Does not fix reply end-of-message ambiguity
### B: Link-level frame writer + cross-task TX (length-prefixed or COBS binary)
Introduce uartLinkWriteFrame() in System_UartLink.cpp owning a link mutex; convert the three existing TX sites (:68-71, :75-80, :290-291) to single-write framed output (type byte + length + payload [+CRC], or COBS with 0x00 delimiters which never appear in text); mic-capture and event producers call it from their own tasks. Extend uartLinkStop to take the same mutex.
Pros: Audio latency decoupled from loop stalls and command execution — streaming-grade; Fixes reply framing (length-prefixed replies) as a side effect — removes the multi-line-reply delimitation hole; ~1-3% framing overhead; raw PCM at 35% of 921600, 16% at 2M; COBS variant keeps text lines legal on the same wire during migration
Cons: Changes the lifecycle model — the loop-task-only invariant (the fix for the HIGH race in the implementation record) must be re-proven with the new mutex; CM5 client must grow a binary frame parser; crash-resync needs a defined hunt-for-delimiter procedure (COBS 0x00 makes this easy, raw length-prefix does not); Frames must stay ≤~1-2KB or a full TX ring makes writers block each other under the HAL mutex for wire time
### C: Dedicated UART-TX service task owning all port writes
One persistent, core-pinned task (per System_TaskUtils.h policy) owns UART_LINK_PORT TX; drain/reply/audio/event producers enqueue frames to it. Optionally later also owns RX via event-driven read, replacing the polled drain.
Pros: Cleanest concurrency story: exactly one writer task, no HAL-mutex contention games, natural priority control for audio vs reply frames; Absorbs loop stalls entirely; enables backpressure policy (drop-oldest audio, never drop replies)
Cons: Heaviest change; tension with the no-per-action-tasks policy (defensible as a persistent service task, but needs the core-split decision) and a new stack/DRAM cost; Reply ordering guarantee (reply follows its command) now crosses a queue — needs explicit sequencing; Lifecycle (stop/baud restart) must coordinate with the task, replacing the sPending simplicity
### D: No transport change — utterance-batch STT over the existing command channel
Record utterances on the XIAO (PDM mic to PSRAM/file), then the CM5 pulls base64 chunks via ordinary commands (~3KB raw per 4095B reply), or the XIAO polls the CM5 for LLM text with batched replies. Request/response purity preserved.
Pros: Zero firmware transport work; works with today's HW-untested but implemented link; No mux, no framing risk, auth model untouched
Cons: Not real-time: a 3s utterance ≈ 96KB raw ≈ 32 reply round-trips ≈ 1.5-2.5s transfer on top of capture — total STT latency balloons; each poll stalls the loop for its execution; Streamed LLM display becomes chunk-poll cadence (a few Hz), not token streaming; files/fileread are admin-gated today — file-based transfer forces the admin-tier decision (plan D3)

## Open questions
- Is CM5→XIAO audio (TTS playback on the XIAO) in scope? If yes, the 4096B RX ring + 200ms loop stalls make today's inbound path unusable at 32,000 B/s — needs a bigger RX ring (settable only before begin), an RX-owning task, or explicit chunk-ack pacing; if STT-only (XIAO→CM5), the hard problems shrink to TX mux only
- Which audio producer feeds the link — the ESP-SR pipeline, raw PDM/I2S capture, or the planned unified mic source layer? Concurrent local wake-word + remote STT contend for the same mic
- Is 2M baud validated on the physical wire (33Ω series resistors, carrier trace lengths, Pi PL011 side)? The plan asserts divider-exactness both ends but nothing is HW-tested — the entire link including 921600 is still pre-HW-validation (plan 'Remaining before merge' item 1)
- Should the mux layer also fix reply end-of-message framing (length-prefixed replies), or does the CM5 client permanently standardize on json-token whole-document replies?
- What is the acceptable audio-loss policy without flow control — drop-oldest with a gap marker frame, or block the producer? And is a future carrier rev's CTS/RTS (reserved GPIO6/7) worth pulling forward for this?
- Is live audio formally S3-only (compile-time gate mirroring UART_LINK_BAUD_MAX), or must classic boards get a compressed (ADPCM ~8,000 B/s) mode?
- For streamed LLM text XIAO-bound: is a push frame type (needs Option B/C) required, or is ~5Hz chunk polling acceptable UX for the G2/OLED surfaces?
- Long-lived stream vs auth lifecycle: should a stream auto-terminate on revocation/logout (per-frame gUartAuthed check), and does a streaming session need exemption interplay with OTA probation (CM5 must stay idle during probation today)?
- Does the planner accept per-frame CRC (the wire has 33Ω series resistors and short traces; UART has per-byte parity available via 8E1 as an alternative) or is framing-only integrity enough at 921600?
